# Testing

The suite checks what the services promise, through their public functions, against a fake provider. Each test describes a behaviour a user or the release process depends on. This page groups the suite by behaviour and names a few files for each. The files' own `describe` and `it` names list every case, and `pnpm vitest list` prints them all.

## Running the suite

```sh
pnpm test                                                              # every test file
pnpm vitest run apps/desktop/test/receiver.test.ts --reporter=verbose  # one file, with each test's time
pnpm vitest run -t "a segment away from the start"                     # tests whose names match
pnpm vitest list --filesOnly                                           # the files a run takes
```

[`test/suites.ts`](../../test/suites.ts) says where test files live: `*.test.ts` under `test/`, `packages/*/test/` and `apps/*/test/`. Vitest runs every one, and [CI](#ci) requires every one in its report, so a new test file needs no list of its own. CI's Check job runs `pnpm knip`, `pnpm lint`, `pnpm fmt:check`, `pnpm typecheck` and `pnpm build`.

Before any test runs, Vitest's global setup, [`catalogue-worker-bundle.ts`](../../apps/desktop/test/catalogue-worker-bundle.ts), bundles the catalogue worker from its source, as the app's build does, and every app a test starts runs that bundle. Watch mode makes none, and starts the worker from its source, so a rerun runs the code as it is. Started from the source files, each worker found and read some 150 modules one by one, a third or more of its start.

Eight files need `ffmpeg` and `ffprobe`: `playback`, `titles`, `receiver`, `output`, `playlist-playback`, `title-filter-playback`, `online-subtitle-playback` and `downloads` in `apps/desktop/test`. They use the ones on PATH, or `MR_STREAMER_FFMPEG` and the ffprobe beside it, and skip their media groups without them. That skip is for a laptop: CI installs both and fails a run where any of them skipped. The setup wizard's test types into a terminal that util-linux's `script` makes, so it runs on Linux and skips elsewhere. `airplay-helper-key.test.ts` runs only on macOS. Tests that run a workflow's bash step skip on Windows.

## What the suite covers

The groups below say what each part of the suite holds the app to, and where to start reading. A change to one of these behaviours belongs in the files named, or beside them.

### Subscriptions and logins

[`subscription`](../../apps/desktop/test/subscription.test.ts), [`playlist`](../../apps/desktop/test/playlist.test.ts), [`credentials`](../../apps/desktop/test/credentials.test.ts) and [`roster`](../../apps/desktop/test/roster.test.ts) run the main process's services against the fake provider and playlist host. A login or a playlist link never reaches the registry, an error the window gets or the diagnostics log. An https address never falls back to http unless the viewer agrees in the Connect screen. The profile is shared with the stable release: `subscription.json` as stable writes it, a write cut short between two files, a damaged registry, and a keychain that lost a secret, which asks again naming only the host. Removing a subscription stops its stream first, takes what was loaded from it and leaves every other one alone, also when two providers number everything alike. In the renderer, `connect`, `subscription-section`, `remove-subscription` and `several-subscriptions` cover the same paths through Settings and the Connect screen.

### Playback, titles and receivers

These need ffmpeg and ffprobe. [`playback`](../../apps/desktop/test/playback.test.ts) runs the local proxy and checks what the player receives for each codec clip, passed through or converted, with its sound and subtitle tracks. [`titles`](../../apps/desktop/test/titles.test.ts) plays movies and episodes from providers with and without byte ranges, with the same decoded picture and start time from either, on one connection to the provider. [`receiver`](../../apps/desktop/test/receiver.test.ts) plays the TV's part: playlists and segments cut at uneven keyframes, and a segment's 30-second deadline. [`output`](../../apps/desktop/test/output.test.ts), [`cast`](../../apps/desktop/test/cast.test.ts) and [`airplay`](../../apps/desktop/test/airplay.test.ts) hand playback to a stand-in Cast device, held to Chromium's schema, and a stand-in AirPlay helper, and leave no process behind. `playlist-playback` and `title-filter-playback` follow a playlist's file and a title's tracks through real playback. Throughout, nothing opens once the viewer moved on or the login changed. The renderer's `receiver`, `receiver-playback`, `output-chooser`, `media-session` and `mini-player` cover the window's side.

### Live player and recovery

The renderer's [`live-recovery`](../../apps/desktop/test/renderer/live-recovery.test.ts) holds a failing channel to reconnects after 1, 2, 4 and 8 seconds, at most four while it only comes back for a moment, never two streams open, and no provider's words or addresses on screen. `paused-recovery`, `title-reading-ahead`, `hls-errors`, `channel-tracks`, `speed-menu`, `live-quality`, `live-more` and `title-scrubber-keys` cover a paused movie letting go of the provider, the player's watchdog deadlines, HLS errors that keep the picture, and the player's keys and menus.

Catch-up: [`catchup`](../../apps/desktop/test/catchup.test.ts) reads which channels an Xtream panel and each playlist convention keep, and checks what reaches the provider when a programme plays from its archive: the panel's timeshift address on its own clock and the minute a recording starts on, each playlist placeholder style, a recording sent at once held back to its playing time, one whose address names no end stopped at the window's end with the provider let go of, a jump of the clock the stream marks as a discontinuity, on the PCR's packet or before it, counted as no time, and the streams of one channel asked from one start, a stream that can't name it left out. Playlist addresses that don't name their start completely, as only an offset before now (`{offset}`, `{offset:N}`, `${offset}`) or a year alone, give no catch-up, and so do addresses that send otherwise than they read, with a fragment, a dot segment, a login or a placeholder before the path, or a query with a `;`, a second `?` or a key twice, however spelt or encoded, as a stream's own `utc` beside the one shift or append adds, while each mode keeps catch-up on an ordinary address, and a channel plays its recordings from its streams that do. `packages/core/test/catchup.test.ts` has the window rules and their errors, [`guide`](../../apps/desktop/test/guide.test.ts) a day's schedule read from its start with what aired in it, one of which plays from the panel's archive for exactly its window, and the renderer's `catchup` the rest of the day's aired programmes, playing one from its start and back to live, reopening it in whole milliseconds from where the provider's recording starts, and stopping at the programme's end.

### Subtitles

`packages/core/test/subtitles.test.ts`, `subtitle-presence` and `subtitle-text-file` decode teletext, DVB, captions, SubRip and WebVTT. ### Downloads

The bounded component diagnostic runs separately from correctness tests: create `.local/download-performance`, then run `DOWNLOAD_PROBE_OUTPUT=.local/download-performance/samples.json pnpm vitest run --config apps/desktop/test/renderer/download-performance.config.ts`. It records 30 React/happy-dom snapshot samples for 520 episodes and 2,000 unrelated downloads. These samples measure component work, not native paint, scrolling or input latency.

[`downloads`](../../apps/desktop/test/downloads.test.ts) needs ffmpeg and ffprobe and runs the main process against the fake provider and a disk that fails as a full or missing one does. A finished download matches the source byte for byte and plays with no provider request. A partial file resumes only when the provider proves it is the same file, and starts again when it was replaced or ranges are ignored. Cancel, retry, deletion, shutdown and subtitles kept with their file are covered too. Its queue group holds a pause to answering once the request ended, its partial kept and nothing taking it again before Resume, through a restart and through playback or a receiver taking the connection; moves to their order through a restart without stopping the transfer; a pause or a move that can't be written down at all to changing nothing, and a pause whose stopping point can't be written to a stopped transfer, its pause kept for the next start; and the download that starts once a held admission lets go to the queue's order by then. `renderer/downloads` covers the Downloads page with its queue's controls and keyboard, and the top bar's notice of a download. The built-app and memory checks are in [Packaged app](#packaged-app) and the [Downloads feature entry](../../.cursor/skills/verify-mrstreamer/features/downloads.md).

### Renderer tests

The renderer's controllers and hooks run in `apps/desktop/test/renderer`, with happy-dom for a DOM and `support.ts` in place of the main process: it records each call, answers the preferences, and holds a call until the test answers it. It stands in for Media Source Extensions too, which happy-dom lacks, with a source that opens and takes no data, so a title's run gets as far as its subtitles. A live stream plays in the element's own engine there: a test moves the element's clock for a picture that moves, and sends the element's `error` event for a stream that stops, with a stand-in for `MediaError`, which happy-dom lacks too. happy-dom refuses a text track's hidden mode and times no cues, so `support.ts` lets a hidden track list its cues, and a test moves the element's clock and sends `seeked` itself. They test what the viewer would see, and media playback does nothing there. hls.js plays nothing there either, so `hls-stand-in.ts` takes its place for the tests of an HLS channel's tracks: it keeps what hls.js promises about renditions, groups, the lines it reads and the segments it says it read, and the [playlist test](#packaged-app) checks the real one in a built app. Where a test needs a run to get further, it puts a stand-in for the title engine that keeps the engine's promises: a run started paused holds its picture. The renderer's tsconfig checks them.

## Deadlines on a busy machine

Vitest ends a test that takes longer than its allowance, 5 seconds unless a suite or a test names another. The title tests and the tests of a movie for a receiver have 20 seconds, and two of the receiver's have 15 of their own. The tests of episode marks on disk have 20 seconds too, since each starts the app two or three times. The allowance covers the whole test: connecting the fake provider, every ffmpeg and ffprobe the test starts, and the waits between them. It is not what a test holds the proxy to. Where the proxy must answer in time, the test sets that wait itself, `segmentMs` or `cuesMs` in place of the app's 30 and 15 seconds, and asserts how long the answer took. Those numbers are the same whatever the allowance.

The tests of a movie for a receiver have 20 seconds because most of their time goes to starting processes and waiting for the provider's connection, and both take longer on a busy machine. One test starts ffmpeg or ffprobe 1 to 10 times, about a tenth of a second each with Ubuntu's build. The fake provider frees its one connection as soon as a request closes. The test of a receiver skipping about asks it to free the connection 50 ms later, as real panels lag, so the request that follows is refused and the proxy asks again 150 ms later, up to 14 times in that test. Leaving out the two with 15 seconds of their own, the slowest takes 2.4 seconds on GitHub's four-processor runners. On a 12-processor virtual machine shared with other work the slowest took 4.3 seconds at a load average of 5, and at a load of 10 to 16 some needed more than the 5 seconds they had then.

When `Test timed out` shows in those two files, look at the machine before running the suite again. `uptime` gives the load. `pnpm vitest run apps/desktop/test/receiver.test.ts --reporter=verbose` runs one file and prints every test's time. On a busy machine most tests are slow by about the same factor. A change that slows every run looks the same, so run the file again once the machine is quiet and compare with the times above. One test far beyond the rest points at that test or the code it covers.

ffmpeg 6, which Ubuntu 24.04 and CI install, switches threads for every packet it copies from a single input, and a virtual machine makes each switch expensive. Copying the 60,000 packets of the large-file test took it 9 to 49 seconds on that machine, 2 with `taskset -c 0` in front, and 1 with `-thread_queue_size 64`. That is why the app passes the option when it reads a title's file, and why the test makes its large file with one. `perf bench sched pipe -T` measures what a switch costs: 35 µs for a round trip there, 12 with both threads on one processor.

## Fake provider and codec clips

`apps/desktop/test/fake-provider.ts` answers like an Xtream Codes panel, with the untidiness of real ones: prefixed names, separator entries, numbers sent as strings, missing logos, one connection at a time. Tests can make catalogue requests fail or change the channels it lists. With `adultChannels`, it adds channels for adults: one the provider flags in an ordinary category, and two in a category named for adults. About half its channels have a guide id, shared by variants of one channel, and `xmltv.php` serves half-hour programmes around the current time. Tests can replace that document, fail it, hold it open or send it in pieces of a few bytes, and count guide and stream requests. Its "TEST | Formats and failures" category streams the clips in `test/fixtures`, plus an offline channel. Its last category, "BE | Kwaliteit", lists one channel in Full HD, HD and SD, the Full HD stream off air. "TEST | H.264 + AAC" keeps three days of catch-up and "TEST | HEVC + AAC" two; the login's answer names the panel's time zone (`timeZone`), and their timeshift addresses send the clip once and end, while `archiveRequests` lists the minutes and start each asked for, and `breakNextArchive` drops the next one part way.

It lists 120 movies and series by default, in their own categories, one of them for adults; one series is marked for adults in an ordinary category. Each carries a TMDB id, its id plus 10,000, except every seventh movie, which has none, and "TEST | Two sound tracks and subtitles 1080p (NL AUDIO)", which shares the MULTI film's and plays the MP4 clip: one film in two versions. "TEST | Formats (EN)" shares the "TEST | Formats (NL)" series' id and lists two of its episodes: one series in two versions. Their files redirect to another address and answer byte ranges, with an ETag, and each open file holds a connection slot. A test can put another file behind a movie's address, give a file another ETag with every answer, have two servers with their own ETags take turns, mark answers with the time they were sent instead, make the provider wait in the middle of a file or before a part that names its end, or have it answer every request with the whole file, as a provider without byte ranges does. The "TEST" movies and the "TEST | Formats" series play the title clips, and one test movie has no file; the rest play the MP4 clip. Tests can fail the lists, or answer them with a refused login as panels do, change what they list as a panel's updates do, with titles dropped, renamed or listed under another id or TMDB id (`serveTitles`), and count file and details requests.

With `second`, it is another provider beside that one, for the tests of several subscriptions: its panel numbers everything as the first's does, so the same id means something else at each. Its channels are the first's, as many as it is asked for, under the same ids and names. Its "TEST" movies are the same films under the same ids, with the TMDB ids the first sends, so each is one title with a version of either. Of its other movies, every second one is the first's next film in English, so under another id than it has there, with the TMDB id the first sends for it, or "0" where the first sends none; the rest are films of its own, "Other Story", with TMDB ids of their own. Its "TEST | Formats (DE)" is the first's series by its TMDB id, with one season of two episodes under the first's own series and episode ids, and its other series are its own.

`apps/desktop/test/fake-playlist.ts` is a playlist host, as a public collection publishes one: an M3U link without a login, three HLS channels, a fourth with Flussonic catch-up when a test asks for `catchup`, whose recordings are four parts in a playlist that names no end yet and whose guide lists half hours, and a guide its first line names only once a test says so. "TEST | Two sounds and subtitles" plays `test/fixtures/hls`, which `apps/desktop/scripts/hls-fixtures.ts` writes with the ffmpeg on PATH: sixteen seconds of test picture in four segments, an English sound rendition at 440 Hz and one at 660 Hz that the stream names only "spa", and English and German WebVTT subtitles, the English ones marked as the stream's default, each with a numbered line from 0.25 to 1.75 s into every two seconds, and French ones that are a header without a line, as broadcasters send while nothing is subtitled. "TEST | Captions in the picture" declares nothing and plays the subtitle channel clip, whose picture carries "HELLO CAPTIONS"; "TEST | One sound" has nothing to choose. Every stream ends, so a line shows at the same second each time it plays.

`apps/desktop/test/fake-guide-host.ts` is a host for XMLTV guides at addresses of their own, apart from any provider, as a guide service publishes them: one file behind an address that carries a key. A test says what each path answers: a document, plain or packed, whole or in pieces of a few bytes, with headers of its own; an HTTP status that fails it; a redirect; or nothing until the test lets go. It notes every request with its headers, so a test can tell that the key went nowhere but there and that nothing of a provider's login came along.

`apps/desktop/test/fake-tmdb.ts` stands in for TMDB: every title it's asked about exists, a comedy when its id is odd and a drama when even, made in Dutch when the id divides by three and in English otherwise. Its names follow the id too (`tmdbName`): English translates all but every fifth title, Dutch all but every seventh, and other languages nothing, so the original name comes back as TMDB sends it. It lists two streaming services, Netflix and Videoland; tests set what Netflix carries, make it refuse every key, and count detail requests, and those a title's details make as it opens, which also get a story, a poster and credits. Every series has two seasons, four episodes in the first and one in the second, named in the series' own language and in Dutch, in English when the episode's number is odd, and "Episode 2" otherwise, as TMDB answers; tests count season requests by series, season and language, and make them fail or never answer. `support.ts` starts services without a key unless a test gives one.

## Installed upgrade

`apps/desktop/test/e2e/installed-upgrade.ts` checks that upgrading an installed Windows app keeps what a viewer had. It has one mode: it installs the newest published stable release, replaces it with a published candidate nightly, then restarts that same candidate. A stable release run makes the check before publishing, with the nightly it promotes as the candidate and the commit it planned to build, which the candidate's tag must name exactly. It can also be dispatched alone from `main` through `.github/workflows/upgrade-check.yml`, whose one input `candidate` is the nightly's tag, such as `v0.0.13-nightly.20261013.300`. It runs on a disposable `windows-2025` runner, with read access alone and no secret, and publishes nothing.

```sh
node apps/desktop/test/e2e/installed-upgrade.ts resolve --candidate "$CANDIDATE" \
  --out "$RUNNER_TEMP/installed-upgrade-packages"
node apps/desktop/test/e2e/installed-upgrade.ts run \
  --packages "$RUNNER_TEMP/installed-upgrade-packages" --root "$RUNNER_TEMP/installed-upgrade"
```

`resolve` needs `GH_TOKEN` and `GITHUB_REPOSITORY`. It refuses a candidate that is not a canonical nightly tag before asking GitHub anything. The prior stable is the newest published stable release by version, from every page of the release list. Drafts, prereleases and nightlies never count, and the check refuses when there is none. Both commits come from their tags; with `--sha`, as a release run passes it, the candidate's tag must name that commit, or the check refuses before downloading anything. Both must be on `main`, the candidate must be a published nightly that strictly descends from stable with a strictly higher version, the release plan's own rule in `packages/contracts/src/promotion.ts`, and each setup must match its asset size and digest, exactly one `SHA256SUMS.txt` entry and `latest.yml`'s version, filename, size and SHA-512. It writes the two setups and `receipt.json` into a new folder. The receipt records the resolved tags and commits, each package's hashes and release metadata, and how far the candidate is ahead of stable. Package receipts are not read.

`run` refuses anywhere but a GitHub-hosted Windows runner with no Mr. Streamer installed, outside `main`, for a receipt of another repository, and in a root that already exists or is not under `RUNNER_TEMP`. It checks both setups against the receipt before installing anything. It installs each with the silent per-user setup into `%LOCALAPPDATA%\Programs\mrstreamer`, on one profile under the root. Each setup is observed as one child of the driver, by executable path, PID and creation time, and must have ended before the app starts. Missing or ambiguous ownership fails. Each start holds main at its first line with `--inspect-brk` and checks it against the owned process and the hashes taken before launch. The window must show the installed app.asar, and the app and Settings > About must name the expected version and commit. Installer, executable, app.asar and bundled tool hashes are recorded.

Every process the app started must have ended before the next setup or start, and each start must close gracefully: a forced termination fails the run. The app is known by its process id and start time from the moment it starts, and its children only through a parent still running under both, so a reused id never makes another program's process the check's. The window is closed as a user would; only if the app stays is it killed, through the handle of the process the check started. Nothing is stopped by its id, which may name another program by then: a child still running twenty seconds after the app fails the run, and is left with the profile for the runner's disposal.

1. On stable, it connects the fake provider, chooses HD, Dutch sound and French subtitles, configures a synthetic SubDL account and opts in through Settings, stars two channels, saves a movie and plays part of it and an episode. While the movie plays it chooses a fixture subtitle and a nondefault offset and drift through the CC panel. It then downloads two movies and the selected S1 E2 file through their details, requires three completed copies with local artwork, and plays them: a skip, the other sound track, embedded French subtitles, the saved subtitle with its timing and shifted cue, and leaving and resuming. It restores the original Dutch sound preference through Playback settings, using General on older releases, and checks all the original settings, favourites, watchlist and provider progress again. Completed-copy details and nonzero unfinished local movie progress are recorded before the installer replaces stable.
2. Before any playback on the candidate, it requires those exact three completed copy IDs, title and episode details, size, local artwork addresses, subscription identity and progress. Progress must keep its null or non-null state and duration, with position less than two seconds from stable's. It captures the inherited copies, then checks the retained settings, favourites in order, watchlist, provider progress and saved subtitle with no new subtitle-service request. It plays the inherited copies without downloading replacements; the first local movie resume must start near stable's saved position, allowing the player's five-second rewind and three seconds for observation. It keeps the post-play state and copies for the restart.
3. The candidate restarts with unchanged executable, app.asar and tool hashes. Everything the candidate left is kept, including the copies, their artwork and their progress. It then blocks outbound connections of the installed app and its bundled ffmpeg and ffprobe with firewall rules named for the run. ## Guide budgets

`.github/workflows/checks.yml` runs on every pull request and push to `main`; [CI](../maintainers/ci.md) shows how it fits with the release workflows.

- **Check:** unused files, exports and dependencies (`pnpm knip`), lint (`pnpm lint`), format, typecheck, the workflows (`pnpm actionlint`) and the production build. Lint, typecheck and tests cover the website's code too.
- **Test:** installs Ubuntu's complete ffmpeg and ffprobe (`apps/desktop/scripts/ci-ffmpeg.sh` fails unless both run and their codecs are there), runs the suite with Vitest's JSON reporter, keeps the report and checks it.
- **Website:** on pull requests, builds the website, installing only what `apps/marketing` declares. On `main`, `publish.yml` builds it after every change to what the page is built from; [the website's README](../../apps/marketing/README.md#how-it-gets-published) describes publishing.

The [release workflow](../maintainers/releasing.md) runs Check and Test on the exact commit it releases, next to the packaged-app test on every installed package. There the production build is the release's own bundle job, the workflows are main's, and the website has no say, so those are left out. CI needs no secrets, so pull requests from forks run it too.

`pnpm actionlint` (`scripts/actionlint.ts`) downloads actionlint and shellcheck at pinned versions, checks them against pinned SHA-256s, keeps them in `node_modules/.cache/actionlint` and lints `.github/workflows` the same way on any machine, with shellcheck on each workflow `run:` script; the shell inside `.github/actions` isn't linted. `test/publication-guard.test.ts` holds the workflows to one rule actionlint can't, by evaluating their real `if:` conditions: nothing a pull request or a dry run starts publishes.

### The test report

`scripts/ci-test-results.ts` finds the test files with `test/suites.ts`, as Vitest does, and fails unless each one is in the report once, with at least one test, every test passed. A media group that skipped for want of ffmpeg fails it, and so do a file that failed to load, a hook that failed after its tests passed, and a test file the run left out. A new test file is required as soon as it exists. The one exception is `apps/desktop/test/airplay-helper-key.test.ts`, which runs only on macOS: elsewhere its tests may skip, but it still has to be in the report with none failed. To hold a local run to the same rule:

```sh
pnpm test --reporter=default --reporter=json --outputFile.json="$PWD/.local/test-results.json"
node scripts/ci-test-results.ts .local/test-results.json
```

Run it from the repository's root. Without ffmpeg the media files fail it, and on Windows so do the files that skip there: the rule is CI's, on Linux.

The Test job uploads the report as the artifact `test-results-<run id>-<attempt>`, kept seven days, whether or not the tests passed. Release runs name it `test-results-<version>-<attempt>`, so a stable run's nightly first and stable release keep a report each. The report's paths are the runner's, so read a downloaded one with `jq` rather than the check:

```sh
gh run download <run id> -n test-results-<run id>-<attempt> -D .local/ci-report
jq -r '.testResults[] | select(.status != "passed") | .name, .message' .local/ci-report/test-results.json
jq -r '.testResults[] | "\(.endTime - .startTime | floor) ms \(.name)"' .local/ci-report/test-results.json | sort -rn | head
```

Files run in parallel, so their times overlap and don't add up to the job's. When no report was written, the tests never ran: the upload warns that it found no file, and the check fails on the missing report.

## Bounded release UI proof

Release dry runs have one Linux `Release UI proof` job after the shared JS bundle build. It downloads the same version-named bundle used by the packages, never rebuilds it, and runs Live TV, titles, Watchlist, Downloads, language, Home and analytics serially through the maintained helpers. Ordinary PR CI and the publication graph are unchanged. The bundle job records the full source revision/tree, stamped app version and SHA-256 of every output file immediately after building. The aggregate compares that receipt and all bytes before and after the scenarios; each scenario must identify the same revision/version/main bytes. A receipt records the build command's provenance, it cannot independently reconstruct a build from a source SHA.

For a local check, use a clean committed source and freshly built output. Only the release's version stamp in `apps/desktop/package.json` may differ from the source commit:

```sh
pnpm install --frozen-lockfile
pnpm build
node scripts/release-ui.ts record "$(git rev-parse HEAD)" 0.0.10
xvfb-run -a pnpm verify:release-ui run "$(git rev-parse HEAD)" 0.0.10 .local/release-ui-success
xvfb-run -a pnpm verify:release-ui run "$(git rev-parse HEAD)" 0.0.10 .local/release-ui-failure --fail-scenario=home
```

Use the actual package version, not the example's `0.0.10`. Each output directory must be empty. `report.json` requires every scenario, a successful original CLI exit, valid proof/actions/observations/screenshots, matching build identity and complete cleanup. Missing, skipped, invalid or failed proof fails the aggregate. It continues after a failed scenario to retain the remaining outcomes. SIGINT/SIGTERM asks the active helper to clean up, then records unstarted scenarios as missing and exits 130. Each child retains `cli.json`, stdout/stderr, its existing `proof.json`, Electron log, screenshots and side effects. Failure injection throws inside the named real-app scenario after a screenshot so its normal failure and teardown paths run; it does not alter product behavior. A child has five minutes plus 45 seconds for cleanup before forced termination, which leaves failed/incomplete cleanup evidence. Doctor has one minute. The workflow's 45-minute limit leaves room for install/artifact setup and the serial bound. Forced workflow termination can interrupt teardown and must never be reported as successful cleanup.

Inspect screenshots with the actions and side effects before accepting visual proof. PNG structure alone cannot establish that the window painted the right state. Home includes local recommendations, empty and hidden-row full Watchlist access, moves and restart. Analytics captures default-on events and Settings opt-out/re-enable on one profile, then refuses local capture on a fresh profile to prove actual pending events are cleared by opt-out and stay cleared across restart. Unpackaged builds honestly report `build_channel: unknown`. Public analytics owner/build tests cover Stable/Nightly attribution. For an available native packaged executable, `node apps/desktop/test/e2e/analytics-app.ts --expected-version=<version> --expected-source=<full SHA> <executable> [app arguments]` drives the same local-capture path, asserts its package version/channel and retains the executable hash and renderer identity. This invocation does not substitute for installed upgrade, signing, native audio/GPU or real-provider acceptance.

Budget assumptions: one Ubuntu runner, one Xvfb display, serial app sessions, Node 24, system ffmpeg/ffprobe, fake provider/TMDB and loopback telemetry. The five-minute scenario limits are failure bounds, not predicted runtime. Measure the aggregate and individual `cli.json.wallMs` on the candidate; count install/download/Xvfb separately when estimating hosted runner minutes. This Linux source-build gate adds one billed job alongside existing package jobs, so its wall time is neither the total release wall time nor the full runner cost. Do not expand it to every normal PR without measuring that cost.

Sources without `scripts/release-ui.ts` are supported only for `0.0.0` through `0.0.10`, including their exact nightly-version form. The workflow explicitly records those sources as `legacy-ineligible`, without claiming aggregate UI acceptance; their original promotion, source and native package checks remain required. A missing helper on any newer or invalid version fails. Sources that contain the aggregate always require all its scenarios, regardless of version. This compatibility rule preserves promotion of earlier tested nightlies and never silently skips a new-source scenario.

Published-pair installed acceptance requires a graceful zero-code app shutdown at each stage. A forced termination remains recorded in the receipt and fails this mode. The legacy chain keeps its explicitly recorded terminated gate.

### Native telemetry acceptance

The [Privacy feature entry](../../.cursor/skills/verify-mrstreamer/features/privacy.md#installed-native-telemetry) documents executable commands, identity pins, real main kills, offline summaries, strict quit, Windows filesystem probes and actual installed .15/candidate sequences. `--native-telemetry` is an explicit long mode outside release-ui. `--native-case` retains selected coverage without claiming the full matrix. Normal package Privacy checks use the existing installed executables and bundled fixture ffmpeg, with artifacts on success and failure. The Windows upgrade workflow runs the frozen .15 compatibility matrix for 0.0.16 candidates through `installed-upgrade.ts telemetry`; it retains the existing resolver, main/disposable-runner guards and deadlines.

A source-built Linux native-mode run establishes actual process and filesystem behavior only for those source bytes. Exact installed Mac/Windows/Linux candidate evidence, native installer transitions, Store-delivered updates and actual nightly production ingestion remain separate release checks. Controlled filesystem promise delay is not measured native slow-disk latency.

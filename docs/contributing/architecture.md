# Architecture

An Electron app in a pnpm workspace, with its website beside it. The main process owns everything that touches the network, the disk and the system; the renderer shows state and starts actions over a typed IPC contract.

```
packages/contracts   @mrstreamer/contracts: IPC schemas, library, guide and movie and series
                     models, errors, versions, updates, the update feed, licences. Depends on
                     nothing else in the workspace.
packages/core        @mrstreamer/core: rules that run without Electron, React or the DOM. Catalogue
                     names and regions, trusted guide ids, the XMLTV reader, the guide and viewing
                     record services, movie and series names, their catalogue, languages,
                     collections and tracks, what the watchlist knows a title by, TMDB's client,
                     update discovery, the provider port,
                     the M3U playlist reader, text folding, and the subtitle decoders: DVB, PGS,
                     teletext, CEA-608.
                     Depends on contracts.
apps/desktop         The app, package name mrstreamer
  src/main           Electron main process
    providers        The Xtream Codes and M3U playlist adapters, and the request for an XMLTV
                     guide at an address of the viewer's own
    services         Subscriptions and their registry, the roster that adds and removes them,
                     library, movies and series, the watchlist, playback proxy, settings
                     (preferences.json), updates, licences
    ondemand         The worker thread that holds the movie and series catalogue and TMDB's
                     metadata
    playback         Stream inspection, HLS playlists through the proxy, the clean start, the
                     sound track choice, captions copied out of the pictures and ffmpeg
                     conversion behind the proxy; probing and ffmpeg runs for movies and episodes;
                     the segments, playlists and indexes a receiver on the network is served
    receivers        The port a receiver adapter fills, and the two that do: Google Cast, a
                     sender of its own, and AirPlay, through the helper in native/airplay
    platform         Keychain-backed secrets, atomic JSON files, the guide store, the database
                     with the viewing and watchlist stores, the electron-updater installer, the
                     diagnostics log
  src/preload        The typed bridge exposed to the UI
  src/renderer       React UI; player/ holds the playback engines, the live and title player
                     controllers, Picture, and the subtitles drawn over it
  src/shared         What main and the renderer share inside the app: window bar sizes
  native/airplay     The Swift helper that plays on AirPlay receivers, one executable for macOS
  scripts            Icons, the DMG background, signing, notarization, ffmpeg builds, third-party
                     notices, the Store package's version, guide and viewing record measurements,
                     the website's demo subscription and captures
  test               Service suites, the fake provider, playlist host and guide host, codec,
                     title and HLS clips, the packaged-app, playlist, several-subscriptions and
                     guide tests, measurements
apps/marketing       The website, package name mrstreamer-marketing: static pages built by Vite
                     from the app captures in docs/assets and the privacy policy in
                     docs/privacy.md. Depends on nothing else in the workspace.
scripts              Release planning, the update feed and CI signing, run from the repository root
test                 The release planning suite, and the website's publishing workflow
```

Packages export their source files by path, `@mrstreamer/core/catalogue/normalize`, and the app bundles them; nothing is built separately. Lint rules keep packages from importing Electron, React or the app, contracts from importing core, and every file from import cycles. `scripts/release-plan.ts` imports `packages/contracts/src/version.ts` and `update-feed.ts` by relative path, because release jobs run it before installing packages.

`@mrstreamer/contracts/ipc` is the contract: each method has an input schema (ArkType) and a result type, and the main process validates every call before its handler runs. ArkType compiles a schema when it's defined, which adds to every start, so schemas the start doesn't need are built on first use: each IPC input on its method's first call. The preload script exposes it as `window.mrStreamer`; the renderer reaches it through `lib/ipc.ts` and React Query hooks in `lib/queries.ts`.

## Data

Everything lives in Electron's `userData` folder, named after the product, not the app id: see the [user troubleshooting page](../user/troubleshooting.md#where-your-data-is). One copy of the app runs per folder: opening it again brings the running copy's window forward, so two copies never write over each other's settings. Each JSON file is written atomically, packed with gzip when its name ends in `.gz`; leftovers of an interrupted write are removed at startup. Changes to these files must stay readable by the newest stable release: choosing Stable on a nightly installs that release over the nightly, and it reads what the nightly wrote. Add fields rather than change a file's version: older readers ignore keys they don't know and keep them when they write. New files are fine: older releases don't look for them. The one agreed exception: Stable 0.0.1 doesn't read `mrstreamer.db`, so it shows no favourites or watch history; Stable 0.0.2 reads it and skips what it doesn't know (see [Viewing record](#viewing-record)). New tables in that database are like new files: older releases never look at them (see [Watchlist](#watchlist)).

A Store copy, an installed MSIX, names its folder `Mr. Streamer Store` instead (`index.ts`). Windows sends files and folders an MSIX package creates under AppData to the package's own folder, `%LOCALAPPDATA%\Packages\MrStreamerOSS.Mr.Streamer_5yzg1erdm3xmr\LocalCache\Roaming`, which Store updates keep and uninstalling removes. Files that already exist in the real AppData are another matter: the package opens and changes them in place. Pointed at a direct copy's `Mr. Streamer` folder on a test runner, the Store copy rewrote its `Preferences`, `diagnostics.log` and the database's shared-memory file, while anything new would have gone to the package's folder. The two copies would have shared, and split, one profile. With its own name, the Store copy starts empty, and the direct copy's folder stays untouched; nothing imports from one to the other.

## Subscriptions

Several subscriptions are saved at once, and every one of them shows in the app together: none is the active one. `services/subscription.ts` (`Subscriptions`) keeps them, and `services/roster.ts` (`Roster`) does what follows from one being added, repaired or removed.

The first subscription saved is the original. Its login is `subscription.json`, as every release has written it. The newest stable release still reads and writes that file, so it stays the only place for that login, its sealed password or link and the account's status, and the original's lists and preferences stay in the files beside it, where that release looks for them. A subscription added beside it keeps the same files in a folder of its own, `subscriptions/<id>`, where no older release looks: its `subscription.json`, the lists loaded from it and what the viewer left it at. `subscriptions.json`, the registry, is a file older releases don't look for either. It lists the saved subscriptions in the order they were added, each with a random id (`SubscriptionSummary.id`), the account the id was given to (`SavedSubscription.key`, the server and username or a playlist's fingerprint) and the name the viewer gave it, and never the password or a playlist's link. The entry marked `original` is the one whose login `subscription.json` holds. An entry this build can't read stays as it found it, in its place.

The files are written one after the other, the login first, and a stable release changes `subscription.json` without the registry. So each start settles them, with the logins deciding (`settle`):

| A login                                      | The registry                                    | Outcome                                     |
| -------------------------------------------- | ----------------------------------------------- | ------------------------------------------- |
| `subscription.json` holds an account         | its original entry names the same account       | the original keeps its id and its name      |
| `subscription.json` holds an account         | names another, has no original or can't be read | the original gets a new id                  |
| `subscription.json` is gone                  | has an original entry                           | the entry goes; the added ones stay         |
| a folder holds a login                       | lists it                                        | the added subscription keeps its id         |
| a folder holds a login                       | doesn't list it, or can't be read               | it is listed again, after the others        |
| a folder holds no login                      | lists it, or not                                | the entry and what is left of the folder go |
| a folder holds a login this build can't read | lists it, or not                                | both stay as they are, and it isn't shown   |
| a folder holds an account saved already      | lists it, or not                                | both stay as they are, and it isn't shown   |

A profile from before the registry is the second row: it gets its id and nothing in it changes. So is a registry that is damaged, which is written anew with every folder's login listed again, a connect cut short between the two writes, and the profile a viewer returns to after a stable release connected another account there. The first row is a password entered again, in either release. The third is a removal there, or one cut short here: a stable release that removes its subscription leaves the added ones, their folders and the registry alone, and so does a downgrade, which shows the original alone until the newer build runs again. An add cut short after its login was written is the fifth row, and a removal cut short the sixth. The last row is a stable release that connected the account of an added subscription: the account shows once, as the original, and the added one's folder keeps what the viewer left it at for when the original is another account's again. Removing the one that shows removes that folder too, so the account doesn't come back at the next start. Nothing else is touched on the way: the viewing record is kept under each account's key, where every release finds it.

The id is what the rest of the app names a subscription by; the account's key stays what its data is kept under on disk. It holds through a new name, a password or link entered again and every restart, and goes with the subscription: the same account added again gets another id and finds its viewing record under its key. A login has a revision too (`SavedSubscription.revision`), a count in memory that rises each time that subscription's login or secret is stored or read anew, and never for a name. What a service asked a provider counts only while that subscription is still saved with the revision it had then (`Subscriptions.stands`, `sameSource`): a catalogue, a guide or movie and series lists that arrive for a subscription that went meanwhile, or that were fetched with the password before, are dropped. Dropped means neither shown nor saved, so the next start reads what this run showed, and a refusal that arrives that late isn't reported as the saved login's. One subscription's revision says nothing of another's: a password entered again for one leaves what is under way for the others alone.

`subscription.add` checks a login with its provider and saves it: as the original when nothing is saved, else in a folder of its own. The account it names decides whose it is: a login for an account that is saved already replaces that subscription's login and keeps its id. `subscription.update` gives a subscription another name, which asks no provider anything, or its password or a playlist's link anew, which is checked first; the server, the username and a playlist's fingerprint never change, since another of those is another subscription. The provider can take its time over a password or link, and what was asked last wins: a subscription removed meanwhile stays removed and the call fails with `no-subscription`, and one whose login was stored anew meanwhile keeps that login, as it keeps a name given meanwhile, and the call answers with the subscription as it is saved. The same holds for a login added again for an account that was saved when it was sent off. `subscription.recheck` asks one subscription's account status, and stores it only while the login it asked with still stands. `subscription.remove` takes one out. A subscription whose password or link the keychain no longer opens stays saved (`needsSecret`): its lists loaded before still show, anything that needs its provider fails with `needs-secret` and its id, and Settings > Subscriptions asks for the secret on its row. The window shows Connect only while nothing is saved.

`Roster` is where the other services come in. Adding one, or entering its secret again, fetches its channels, then its guide and its movies and series in the background, while what plays goes on. Removing one ends what plays from it first, on a receiver and here, then has it saved no more, deletes its account's [viewing record](#viewing-record) when asked, then its login, then what the library, the guide, the catalogue worker and the settings hold of it; what plays from another subscription never notices. At startup it brings every subscription up to date, two at a time, each on its own: the account's status, and the channels, the guide and the movies and series that are older than 12 hours. One that can't be reached holds no other back.

### Whose a channel or title is

A provider's ids are unique only within its own lists. So everything a provider lists is named in full by an `OwnedId`: the subscription's id, and the provider's id as it sent it. Channels, categories, titles, each version of a title and episodes carry both; requests name them the same way; answers per channel are keyed by `ownedKey`; and the window's query keys hold both. `TitleRef`, what plays on demand, has its subscription beside its ids.

Two providers number alike, so the same id at two subscriptions names two different things, and every lookup goes by both parts. A request that names a subscription that isn't saved finds nothing. Asked for alone, it fails with `no-subscription`: a channel, a title's details or file, a stream to open, a favourite, a watch or progress to record, a title to save or take off the watchlist, a subscription's preferences. Lists leave out what isn't theirs: channels and titles by id, guide listings, progress. So what was under way for a subscription that was removed, such as a late progress save from the window or from a receiver, never plays from another and never lands in another's record. An open for such a channel fails before it closes what plays.

On disk nothing inside a file is named by the subscription's id: the id only names an added subscription's folder. The caches, the viewing record and the watchlist keep the provider's ids as they came, under the account's key, as the stable release reads them. The services add the subscription's id on the way out and take it off on the way in.

There are two kinds of settings. Preferences hold whichever subscription plays (`preferences.get`), and live in `preferences.json`. What the viewer left a subscription at is that subscription's alone, since every id in it is its provider's: the last channel and category, the versions picked for titles and the streams picked for channels (`subscription.preferences` and `subscription.updatePreferences`, which name the subscription). The original's are in the same flat `preferences.json`, where the stable release looks for each, and an added subscription's in the `preferences.json` of its own folder. Each call checks that the subscription it names is saved when its turn at the file comes, so a change that waited while its subscription was removed fails with `no-subscription` and writes nothing. Removing a subscription forgets them (`Settings.forget`).

## The login on the wire

The address of a guide the viewer adds in Settings > Guides is a secret of its own, apart from any login: see [Guides from other addresses](#guides-from-other-addresses). Its request never goes through `providerFetch`, so nothing of a provider's login travels with it.

Xtream panels take the login in every address: the API and the guide in the query, streams and files in the path. Every request to the provider goes through `providerFetch` in `@mrstreamer/core/provider`: the adapter's own, and the proxy's through `Provider.request`. It follows redirects itself. After an https address it refuses a redirect to an http address whose path, query or user info holds the username or the password (`exposesLogin`), so the login never travels unencrypted once the viewer typed https. A redirect to http that carries only a token of its own, as panels send for streams, is followed; refusing every https-to-http redirect would be a one-line change there. The error says why, and nothing falls back to http. Its errors, and the adapter's, cut any address they quote to its origin (`withoutAddresses`), so a message from fetch can't carry the login to the window, the console or the diagnostics log. An address typed without a scheme means https (`parseLogin`). When the login check there fails for a reason http might not share, such as no TLS on that port, no answer, an invalid certificate or something other than the API, `Subscriptions.add` fails with `unencrypted-only` before the login goes anywhere else (`httpsUnavailable`); a refused login or a name that doesn't resolve fails as it is. A firewall that drops the https port's packets instead of refusing them holds that answer back until the request gives up, ten seconds or more. So a bare TCP connection to the port runs beside the check (`connectionIgnored`). Once the name resolved, three seconds without the port accepting or refusing end the check with `unencrypted-only`. A server that accepted keeps the login's 15 seconds, however slowly it answers. The form then asks once, on the Connect screen and in Settings > Subscriptions alike (`features/connect/LoginForm.tsx`), and Connect without encryption sends the address again with `http://`. An address typed with `http://` connects as typed, with a line under the field saying the login travels as plain text, and a subscription's details in Settings note an http login as not encrypted.

## Catalogue

The library fetches each subscription's categories and channels, indexes them in memory and caches the provider's raw answer in that subscription's folder; display names are worked out on load, so naming rules improve without a refetch. A refresh replaces a catalogue only when it looks complete: an empty answer never does, and one with less than half the channels only when a second fetch agrees. A failed refresh keeps the catalogue and reports the failure in that subscription's status, with when it failed. Favourites and history refer to provider ids, so renamed or reordered channels keep them.

Each stream keeps the provider's guide id (`epg_channel_id` on Xtream panels, `tvg-id` in playlists). Quality variants of one channel usually share it, but panels also file unrelated channels under one id: one provider lists nine Flemish channels under `PlayCrime.be`. `@mrstreamer/core/catalogue/guide-ids` keeps an id for a stream only when its name matches the id, or when every stream sharing it is the same channel under another name or quality. The guide's own channel names don't count: panels copy them from their stream list. On that provider this keeps 1,978 of 2,073 channels with programmes. A cache saved before guide ids existed still loads, and counts as due for a refresh at the next start.

### Several subscriptions

Every list the library serves is of all saved subscriptions together (`combine` in `services/library.ts`), made from each one's own index and made again only when one of them changes:

- **Channels** stand in blocks, the subscriptions in the order they were added, each block in its provider's order. Nothing is joined across subscriptions: the same channel at two providers is two channels, which may play differently and are watched on different connections. Each keeps its provider's own number, so two can share one: a number typed in Watch goes to the first channel that has it, in this order (`features/watch/NumberEntry.tsx`).
- **Categories** join when they read the same: the same country or group, the same title, and both for adults or neither. A joined category has the id of its first member and lists every member (`Category.members`); asking for the channels of any member answers the joined list, so a category remembered from before another subscription arrived still opens.
- **A channel that reads like another subscription's**, by the title the lists show, is marked `ambiguous`. The window says whose it is on such a channel alone (`useSourceOf` in `lib/queries.ts`): a row, a search result, Watch and a favourite's tile name the subscription, and a channel nothing else reads like says nothing more. Movies and series are marked the same way.
- **Search** ranks the channels of every subscription together before it cuts the list, so one subscription's matches can't crowd out a better one of another.
- **One that fails holds nothing back.** A list is answered from the catalogues at hand, and a subscription whose catalogue is neither in memory nor on disk is fetched in the background; a call waits, or fails, only when no subscription has anything to show. `library.status` answers one status per subscription, and Live TV says in one line which subscriptions couldn't be fetched, with Retry (`SourceNotices` in `features/live/GuidePage.tsx`). At most two catalogues are fetched at a time, and a second request for one that is being fetched joins the first.

### Channels for adults

A channel is for adults when one of its streams is: the provider sets `is_adult` on it, where its live list has the field, or it sits in a category named for adults, by the same rule as movies and series (`@mrstreamer/core/adult`). The library marks such a channel `adult` and, while `adultTitles` in the preferences is off, serves a view without it, nor categories left empty without it: no list, category, favourite or recent entry, channel by id, guide row or count shows it, so the last channel can't reopen it on start. With the setting on, Live TV's lists and guide show it, and the search of a list there finds it, but ⌘K's channel search and programme search still leave it out, and Home leaves it out of its rows and its backdrop and plays no preview of it. The viewing record's lookup sees every channel, so favourites and history keep their entries either way. A cached catalogue from before the flag counts as outdated, so the next start refreshes it.

### Channels with several streams

Panels list a channel once per quality, "VRT 1 FHD", "VRT 1 HD", "VRT 1 SD", with backups ("FHD²") and sometimes a category for a quality ("BE | 4K"). `@mrstreamer/core/catalogue/variants` makes one `LiveChannel` of streams that are surely one channel, its `variants`, and leaves anything less certain apart:

- Their titles agree once quality markers are gone. Case and accents don't count; spaces and symbols do, so "Canal+" stays apart from "Canal", and "VRT1" from "VRT 1".
- Their regions agree: the name's or category's, else the country of a trusted guide id (`VRT1.be`). A stream that names no region joins the one region group there is, never two.
- Their languages agree ("BE - FR |"), and none only matches none.
- Their categories hold the same thing, quality words aside: "BE | VLAANDEREN" and "BE | VLAANDEREN HD" do, "CA | FRENCH" and "CA | ENGLISH" don't. A stream in a category named only for a quality joins the one group there is, or stays with its kind beside several.
- Their trusted guide ids don't disagree, a feed's quality aside: playlists' `Colors.in@SD` and `Colors.in@HD` agree, `@East` and `@West` don't. Nor does their spelling count: one panel writes `vtm.be` on a channel's Full HD stream and `vtm BE` on its HD one, so case, spaces and punctuation are left out, while every letter and digit stays, the country's too, and the symbols titles keep. A shared guide id joins nothing by itself.

A channel's id is the lowest of its streams' ids, so the provider reordering them changes nothing, and the library finds a channel by any of its streams' ids. It shows in every category one of its streams is in, where its first stream there is; search reads every stream's name. Its guide ids are its streams' trusted ones, each spelling once in their order, and it shows the programmes of the first the guide has any for, so a spelling the guide doesn't know never hides one it does. Its `tags` are those every stream carries. On the public iptv-org playlist of 2 October 2026, 11,152 entries make 11,009 channels: 143 channels with an SD and an HD feed, while 14 pairs with one name stay apart, as different countries, regional feeds or a separate 4K channel.

A stream's `quality` is what its name says (`qualityOf`): 4K, UHD, 8K and 2160p are 4K, FHD and 1080p Full HD, HD and 720p HD, SD and lower line counts SD. A line count is the more precise, so "HD (1080p)" is Full HD. Markers that say nothing about the picture, as "HEVC" or "RAW", or disagree, as "HD (576p)", leave it null, which the UI shows as "Not labelled". A playlist's `@SD` feed says nothing either: those are often 1080p.

## Playlists

A link the Connect screen gets without a login, in the fields or in its query, is a playlist (`parseLogin`): an M3U file such as iptv-org's, which starts with live TV only until its groups are explicitly mapped from 0.0.9. A server address alone, without a path, still asks for the login. `providers/m3u.ts` reads it as it downloads, a piece at a time, with `@mrstreamer/core/playlist/m3u`, and `@mrstreamer/core/playlist/catalogue` turns its entries into the catalogue every adapter gives. Groups are categories, several to an entry when `group-title` separates them with ";", as iptv-org does. The tvg-id is the guide id, `@Feed` included. In the unmapped catalogue, names stay exactly as written, so the catalogue reads "(720p)" and "[Geo-blocked]" from them as it does from a panel's names. A stream's id is its tvg-id, else its name, so favourites and history follow it across refreshes; the catalogue joins the streams of one channel as it does a panel's, as "Colors (576p)" and "Colors HD (1080p)". Entries no player here plays are left out: DASH and addresses other than http(s), 136 of iptv-org's 11,152. In a historical 0.0.8 measurement on one machine, reading that 2.5 MB list into the library took 620 to 730 ms and held the main process 56 ms at most, against 510 to 530 ms and 160 ms for the fake panel's 13,000 channels. Those timings predate the 0.0.9 import path and do not measure mapped or 100,000-entry imports.

The link can hold a token, so `subscription.json` keeps it sealed like a password, with its origin to show and `m3u:` plus part of its SHA-256 as the account's key, under which the caches and the viewing record keep its data. Stream addresses stay out of `catalogue.json` for the same reason: the adapter holds them from its last read, and reads the playlist again for a channel the library loaded from disk after a restart. Each request for a channel's stream carries the User-Agent and Referer its entry names, in its attributes or `#EXTVLCOPT` lines. The guide is the XMLTV document the header names (`x-tvg-url`, `url-tvg`), unpacked when it is gzip. The adapter reads the playlist's first line again each time the guide is asked for, and no more of it, so a guide the publisher added, moved or dropped is found; a playlist that names none answers that it has no guide (see [Programme guide](#programme-guide)). Unmapped playlists answer empty movies and series; the top bar shows Home and Live TV only while every saved subscription is an unmapped playlist. From 0.0.9, explicitly mapped playlists also enable Movies, Series and Watchlist without an Xtream login. Releases before playlists read a playlist's `subscription.json` as no subscription and show Connect, leaving every file as it is.

From 0.0.9, `subscription.json` keeps the authoritative optional `mapping`, with group digests and Live TV, Movies, Series or Skip choices. `@mrstreamer/core/playlist/import` applies those choices without guessing from names. New groups wait; conflicting groups and uncertain entries stay out with bounded names and reasons. A playlist without mapping uses the original Live-only catalogue without exact-title hashing or mapping reports. Explicit imports and Settings mapping inspection enforce 100,000 entries, 64 MiB of unpacked text and 10,000 groups. Inspection uses the last read when available and constructs its report on demand; otherwise its download enforces the mapping limits. A rejected inspection or first pick saves no mapping and leaves unmapped Live usable, including oversized sources and stream resolution after restart. Mapped movies and episodes need supported finite files; HLS `.m3u8` entries stay out of those groups.

`Roster.refreshPlaylist` supplies one typed main-process import snapshot to Library and OnDemand. Each consumes that snapshot after its own fetch slot is free. A titles query joins the active title refresh through acceptance; another supplied snapshot waits to be accepted in order. An unmapped combined refresh joins a Live fetch already running and needs no title snapshot. Independent refreshes outside that combined operation can read again. Failures keep prior lists, while successful mapped empty imports clear them. Both `catalogue.json` and `ondemand.json.gz` keep `importRevision`, so a mapping saved before an interrupted refresh is detected at the next start.

Series accept one bounded unambiguous `S01E02` or `1x02` token. Ordinary opening brackets before that token are separators; meaningful title prefixes, such as a year or edition in brackets, remain part of the series name. Episodes keep source order across interleaved seasons and specials. Exact file ids use the complete raw entry name, address, attributes, group and headers. Changing even a logo address creates a new version; progress is conservatively kept apart. Optional `files` in stored series listings preserve those identities through reorder and restart, so a replacement file inherits no progress. The main adapter owns playable addresses and exact headers; the worker receives no file addresses or headers. After a restart, resolving a file reads the playlist again.

## Movies and series

`services/ondemand.ts` (`OnDemand`) owns movies and series. Their lists are large: 53,000 movies (21 MB of JSON) and 10,000 series on a large provider. Reading, indexing and sorting them on the main thread stalled it for 100 to 300 ms, so the catalogue lives in a worker thread, `ondemand/catalogue-worker.ts`, started on first use (electron-vite bundles it through `?nodeWorker`; tests start the source file). The worker fetches both lists with its own copy of the Xtream adapter, parsing each in one go, which off the main thread is several times faster than reading row by row. From 0.0.9, a mapped M3U playlist instead supplies its title catalogue from the main adapter, including the shared snapshot for a combined refresh. The lists it fetched wait aside until the main process, which knows the saved login, says they still count (`finishRefresh`); the worker then answers and keeps them in that subscription's `ondemand.json.gz` as the provider sent them, 3.3 MB packed instead of 17.7. All pending lists share one wait, a second after the last arrived. A key change or quit skips that wait and gives the worker up to 2 s to write every pending cache before stopping; a write cut short leaves the previous lists, which the next start refreshes when due. For Xtream, an empty answer replaces lists that had titles only when a second refresh agrees, and a list answered with a refused login fails the refresh instead of counting as empty. The lists refresh at startup after the live catalogue and the guide when they are older than 12 hours, and when first needed.

There is one worker, however many subscriptions are saved. It holds each subscription's lists apart, by its id, read from and written to that subscription's own folder, and one index over all of them for what the window shows. A call that reads the index names the subscriptions whose lists count (`owners`), in their order, with the account each is kept for and its folder; a refresh, a details call and a removal name one. So an answer holds only what is saved now, and every title and version in it says which subscription lists it. One subscription's lists fetched again index the others' rows anew without parsing them again, and at most two subscriptions fetch at a time, a second request for one joining the first. A subscription whose lists couldn't be fetched leaves the others' titles showing: `ondemand.status` answers one status per subscription, and a call fails only when no subscription has lists to show. Unmapped playlists have no titles and are never asked. Explicitly mapped playlists participate from 0.0.9, even when their current mapping imports no titles.

Nothing depends on a field only some providers send. The worker reads what Xtream Codes panels list for every movie and series, names, dates, ratings, artwork and the TMDB id (`tmdb`), and asks TMDB for the rest. The provider's categories aren't shown.

### Titles and versions

`@mrstreamer/core/ondemand/catalogue` indexes the lists for one language, each kind when first read. Display names are worked out on load (`@mrstreamer/core/ondemand/names`: "Blow 2001 (NL)" is "Blow 2001" with the tag NL), so naming rules improve without fetching again. Providers list each language version of a film as its own stream; rows sharing a TMDB id become one title with its versions inside, and rows without one stay on their own. That holds across subscriptions too: a film two of them list under one TMDB id is one title, whose versions name their subscriptions, while nothing is ever joined by its name, and the same provider id at two subscriptions is two titles unless TMDB's id says otherwise. A title is known by `Title.key`, the kind with its TMDB id or, without one, with its one version, so a tile stays the same tile whichever version it shows. Two titles of different subscriptions that show under the same name and year, without being one, are marked `ambiguous` and say whose they are. Collections, search and their counts are worked out over these titles, joined first and cut after, so a page or a total never counts a film twice. A title shows the version that suits the viewer's language best (`@mrstreamer/core/ondemand/languages`): marked with the language, then marked for several, then marked for a language that subtitles rather than dubs, then unmarked, then dubbed into another, the newest first among equals. Dutch, Flemish included, subtitles: "(NL)" on an English film is English with Dutch subtitles, unless the mark says otherwise, as "(NL AUDIO)". A row for adults never joins the others, so the film's other versions stay. The language is `titleLanguage` in the preferences, English by default, and changing it indexes again. Every version finds its title, details belong to the version they were opened for, and progress counts across the versions of one subscription: `viewing.progress` takes every version of a series. Another subscription's version is another file, with its own length and its own episodes, so where one stopped is never where the other resumes (`ownProgress` in `features/titles/DetailsView.tsx`): it starts from its beginning, and keeps a position of its own from then on.

A version the viewer picks is `titleVersions` in the preferences of the subscription that version is of, by kind and TMDB id, `"movie:603"`, to the version's id; only titles with a TMDB id have several. Picking one takes the title's pick out of every other subscription that lists it, so one version is picked at most (`usePickVersion`). The details sheet works out which version plays before asking for details: `ondemand.titles` gives the title with its versions from the lists, then an explicitly asked version, as the 4K tab and filtered tiles ask for their displayed version, else the pick, else the version the sheet was opened on when it differs from the first, else the version a movie stopped in partway or a series was watched in last, else the best suited (`lib/titles.ts`). A choice in the sheet's own menu wins over that order and stays after playback or Settings. It shows that version's details, so a series lists the seasons and episodes of the subscription that plays, and never another's. Continue watching resumes the version that was played, in its own subscription, and plays a pick only when it is of that subscription. A pick the provider no longer lists counts as none, and removing a subscription forgets its picks. Nothing falls back to another subscription by itself: a version that fails says so, with the menu beside it. From 0.0.9, `versionOptions` in `@mrstreamer/core/ondemand/version-options` orders the menu by quality, language hints and saved subscription order. `versionHint` supplies what each version sounds like and its subtitles, from its marks and the title's `originalLanguage`: "(NL)" on an English film is "English sound, Nederlands subtitles", on a Dutch one "Nederlands sound", and "(NL AUDIO)" "Nederlands sound" either way. A mark followed by SUB names the subtitles in any language: "(ENG SUB)" on a Korean film is "한국어 sound, English subtitles", and suits English viewers without counting as dubbed for others. Equal hints within a subscription fold into a disclosure that keeps every distinct exact file selectable with its original name, container and listed date. Source-list order numbers the files consistently in the menu and under Play. Locally read tracks replace only that file's hint; a series summary explicitly counts read files, including alternate files of one episode. Every menu row names its subscription at the right. The line under Play names it when the versions are of more than one subscription. Automatic's line names the version it plays.

Titles the provider marks for adults, or that sit in a category named for adults, are left out of every collection but their own, `adult`, and of search. That one answers empty unless `adultTitles` in the preferences says to show them; Movies and Series then show an Adults tab. A category is named for adults when its name holds one of a short list of whole words, in the languages of the panels seen so far (`@mrstreamer/core/adult`: XXX, porn, porno, 18+, +18, adult, adulte, adulto, adulti, Erwachsene, volwassenen, with their plurals; "Adult Swim" isn't one). A category list that comes back empty keeps the one before, so a busy panel doesn't unmark them. The worker asks TMDB about titles for adults only while `adultTitles` is on: each status call tells it, and turning the setting on asks about them from then on.

### Local track observations and filters

`platform/verified-files.ts` stores `verified_files` in the shared SQLite database. Each row belongs to an account and exact movie or episode file, with the current listing revision and source fingerprint. Playback writes only tracks it actually read. A fresh session id guards writes and erasure against a late answer from an older playback session. Changing a source, repairing an account or replacing a listed file invalidates its old observations.

`ondemand.filterOptions`, filtered collections and `ondemand.titles` read those observations without opening files. Details and seasons decorate exact episode alternatives from the same validated facts. The worker caches current listing maps per kind and catalogue; a title lookup with no observed tracks stays a direct index lookup. Observation-only lookups skip episodes without a stored file fact before hashing or parsing their names. Filter queries still inspect all current episode listings for unread hints. Main validates episode facts against retained current series details; the catalogue worker validates movie facts against current listing rows. Name hints and observed tracks remain separate. Unknown verified language means a track was read with no language tag, rather than an unread file.

### TMDB

`@mrstreamer/core/metadata/tmdb` is TMDB's client: one title's details (genres, original language, popularity, rating and votes, franchise, backdrop, its name in a language and its original name), a season's episodes, and which titles each streaming service carries in a region, from TMDB's watch providers, whose data comes from JustWatch. A read access token goes in the Authorization header, an API key in the query.

`ondemand/metadata.ts` keeps what collections use in `metadata.json.gz`, inside the worker. After the lists load, it asks about each listed title once, newest first, 8 at a time and at most 40 a second, waiting when TMDB asks it to and trying twice more after a failure, 15 s at most per request. After 24 requests in a row without an answer, offline or with TMDB down, the run stops until the next start or refresh. It asks in the viewer's language and keeps each title's name per language, so a title counts as answered once it has a name in the language chosen now: changing the language asks every title once more, in the background, and changing back asks nothing. TMDB answers with the original name when it has no translation; that counts as none, and for a title made in neither English nor the viewer's language the English name is asked for too. Titles show the translation, else the original name when it is in the viewer's language, else the English name, else the original, else the provider's name without its marks (`metadata.name`). Search finds titles by every name TMDB gave them as well as the provider's: `ondemand.search` gives the palette the first 60 of each kind, and `ondemand.searchKind` gives the field in Movies' or Series' tabs the first 300 of its kind, with how many match. It asks again after 150 days, and stops using and keeping anything after six months, TMDB's limit. A list given while it fetches, as after a refresh, takes over, ahead of the streaming services. Those, the 12 most prominent per kind in the system's region with their 5,000 most popular titles each, are fetched again after a week. It saves every 30 s while fetching. It also decides what the UI is told. The kept file counts as content once it has loaded, if it holds anything lists show, so collections built before it are rebuilt even when nothing needs fetching. A refetched entry that is the same apart from its time is saved and told to nobody; one that had expired is always content, as lists built before and after differ. A change in the status alone (an id TMDB doesn't know, a refusal, a run ending) goes at most every 3 s as `ondemand.progress`, which carries only TMDB's part of the status and merges into the status the UI has, leaving the lists' as they are. A change in what lists show goes as `ondemand.updated`, which has every open list read again from the whole library, so these start 3 s apart and double with each one during a run, up to 30 s; the spacing starts over with each pass of the run, as for a new list or language. Every answer checks whether content not yet told is due, so a changed title is not held behind unchanged ones; while TMDB asks to wait, nothing arrives and it waits for the next answer. Forced notices (the services, the end of a run, a refusal) are not held to the spacing and carry what is not yet told, so lists are current at the end. A refused key stops it until the key changes. Settings > General shows how far it got, and so does a ring beside search in the top bar (`components/TmdbProgress.tsx`), only while titles are being asked about: the status says whether a run is going.

The key is the viewer's own from Settings (`tmdbKey`), else `MR_STREAMER_TMDB_KEY` at run time, else the one built in from the release's `TMDB_API_KEY` secret (see [releasing](../maintainers/releasing.md#tmdb-key)). Changing it restarts the worker. Without a key, movies and series work without genres, services or popularity.

### Collections

`@mrstreamer/core/ondemand/collections` builds a kind's collections for a language from the titles and the metadata so far:

- All, every title but those for adults
- For adults, only once the viewer turns them on in Settings
- New this week and this month, by the date the provider added them
- Recent releases, from this year and last
- Popular, by TMDB's popularity
- Top rated, 7.5 and up on TMDB once 100 people voted; the provider's rating only sorts titles TMDB doesn't know
- 4K, titles with a version marked 4K or UHD
- each genre and each streaming service, `genre:Comedy` and `service:8`
- titles like one, `like:` and one of its versions as `ownedKey` writes it: the most genres shared, then the most popular

Every collection but All holds only titles that suit the language: a version in it or in several, or one with its own sound or unmarked that TMDB doesn't place in another language. New counts the date a version arrived unless it is a dub into another language. The worker builds them when first asked and again after more metadata arrived, and answers three calls. `ondemand.rows` gives a tab's rows: For you starts with titles like the one watched last, then popular, new this week, top rated and the three best-stocked services; New has this week, this month and recent releases. `ondemand.tiles` gives the genres or services with their counts and a picture. `ondemand.collection` gives a page of one, in its own order or by date added, popularity, rating or name.

Details come from the provider when a title opens (`get_vod_info`, `get_series_info`), never before: nothing loads them on hover or keyboard selection. TMDB is asked at the same time, in the viewer's language with the credits (`tmdb.about`), for at most 4 s; its original name, overview, poster, backdrop, genres, runtime, cast with portraits and directors or creators come first, the provider's fill in, and the provider's seasons and episodes stand, since they are what plays. A provider's length is only what its panel says of the file and can be far off, so it shows where TMDB has no runtime; playback and saved progress go by the length ffprobe measures (see [Movies and episodes](#movies-and-episodes)). The details don't wait for TMDB: `ondemand.details` answers once the provider has, with what TMDB said by then. When TMDB answers later, the main process sends `ondemand.detailsChanged` with the version's kind and `OwnedId`, and an open sheet reads its details again. While the provider answers, the sheet shows the title from the lists: its name, year, rating and artwork. A season's episodes wait for TMDB's answer only when they need the series' own language and the lists don't know it yet. The provider's original name counts only when TMDB didn't answer, without its version marks, and when it differs from the shown one: panels often repeat the stream's name there. Both answers stay in memory for the last 200 titles, so a title opened again asks no one, with two exceptions: TMDB is asked again when it didn't answer, or there was no key, and the provider is asked again once the lists were refreshed since, as it may list new episodes; if it fails then, the details from before stand. The details are put together each time with the title as the lists show it then, so its name and original language follow TMDB's metadata as it arrives. The UI marks details stale when the lists change, and reads them again the next time they open. Continue watching takes its titles from the lists (`ondemand.titles`, through the worker), so Home asks the provider nothing for it; an episode's series details load when it is resumed. `@mrstreamer/core/ondemand/details` builds a series' seasons from its episodes, because panels list seasons incompletely or not at all, and puts specials last. Some panels list two files of one episode, as after uploading it again; the sheet shows one, picked as a title's version is: the one whose name's marks suit the viewer's language best, then the newest. The other still plays by its id, as from Continue watching, and its progress shows on the episode's row, matched by season and number. `OnDemand.file` names the provider file a movie or episode streams from; the URL holds the login and never leaves the main process.

An episode gets TMDB's details only when the viewer opens its season (`ondemand.season`, `tmdb.season`): its name in the viewer's language, story, still, air date, runtime, rating once five people voted, guest stars and directors. One request asks for the whole season in the viewer's language. TMDB names an episode it has no translation for "Episode 3", which counts as no name; while an episode TMDB lists has none, the app asks for the season in English, then in the series' own language, as titles' names fall back. The provider decides which episodes exist and in what order: one TMDB lacks keeps the provider's details, and one only TMDB lists doesn't show. TMDB's runtime comes before the provider's length, from the first answer that has one, and the provider's story before one in another language. Each request waits at most 4 s; a season TMDB didn't answer shows the provider's episodes and asks again the next time it opens. Answers stay in memory for the last 100 seasons, by TMDB id, season and language, so a season opened again, or in another version of the series, asks no one. Nothing goes to disk, and removing a subscription forgets what was kept for its titles. The details sheet asks for the season it shows, and for another when its tab opens, each time it shows (`queries.season`), but not as more metadata arrives. Its rows show the provider's episodes until the answer comes and then grow together; they keep their top, so the browser's scroll anchoring holds what is in view.

## Interface language

The app's own text comes from one catalogue in `@mrstreamer/core/i18n`, in the five languages of `LOCALES` (`@mrstreamer/contracts/language`): en-US, nl-NL, fr-FR, de-DE and es-ES. A message's key is its English text, `t("Check now")`, and its {placeholders} are typed parameters: `t("{known} of {wanted} titles", { known, wanted })` fails to compile without both. Words that change with a number have plural forms, picked by the language's `Intl.PluralRules`, and take `count`. `i18n/en.ts` is the source; each other language is a `Translation`, so a message added in English fails the build until every language has it, and a message missing at run time shows in English, then as its key. Numbers, percentages, sizes, dates, times, lists and language names are written only by the formatters beside `t` (`formatNumber`, `formatDate`, …), which keep one `Intl` object per language and kind.

Each process has one language at a time (`setLanguage`): the window, the main process and the catalogue worker. Text is made where it was made before, in the language of that process: the window renders its own, the main process writes the error details it sends, track names and the macOS menu, and the worker its collection names; the worker gets the language with every call. Text made from what comes from elsewhere stays as it came: titles, channel and provider names, TMDB's metadata, track languages (named in their own language) and what a server, ffmpeg or the system said.

The main process owns the choice. `preferences.json` keeps it as `interfaceLanguage`, "system" or a locale, as any string so a language a later release adds doesn't drop the file; only `language.set` writes it, and `Preferences` doesn't carry it. `resolveLanguage` makes it a language: a saved locale, else for System default the first of the system's languages the app speaks (nl-BE is Dutch), else English, and English for a value this release doesn't know. Dates and numbers use the system's own variant of that language where it has one (en-GB, de-AT). The window asks for it before its first paint (`language.get`); after Settings changes it, the root renders again in the new language, so what plays goes on playing, and queries are fetched again for what the main process wrote in the old one. A sentence the main process wrote before the change, such as a failure's detail or the track names of a title already open, stays as it was written until it is made again. On macOS the menu bar is rebuilt in the new language; the system draws some of its items, and its permission prompts, in the system's language among those the app is packaged with (`electronLanguages`, and `build/locales/*.lproj/InfoPlist.strings` for the local network prompt). The save dialog gets its title, button and filter in the interface language; its other words are the system's.

A translation is corrected by changing its line in `packages/core/src/i18n/<language>.ts`; the English text stays the key. The first translations were made by machine for 0.0.10.

## Effect services

The main process runs every service on one [Effect](https://effect.website) runtime (`effect` 4, pinned to a release candidate). `apps/desktop/src/main/runtime.ts` assembles them from Layers in `mainLayer`. `index.ts` makes the runtime at start, forwards each service's changes to the window, and registers the IPC handlers: each returns an Effect, and `ipc.ts` runs it on the runtime.

| Service         | Where                              | Owns                                                                                                                                                                                                                                                    |
| --------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Subscriptions` | `services/subscription.ts`         | Each saved login with its sealed password, or a playlist's sealed link, the id the app names it by, its name, the provider behind it, and the account's status: asked at startup and again when Settings > Subscriptions opens (`subscription.recheck`) |
| `Roster`        | `services/roster.ts`               | What follows from a subscription being added, repaired or removed, and bringing each up to date at startup                                                                                                                                              |
| `Settings`      | `services/preferences.ts`          | `preferences.json`: the preferences, and what the viewer left each saved subscription at                                                                                                                                                                |
| `Library`       | `services/library.ts`              | Each subscription's catalogue, its cache and refreshes, and the lists of all of them together                                                                                                                                                           |
| `OnDemand`      | `services/ondemand.ts`             | Movies and series, through the catalogue worker                                                                                                                                                                                                         |
| `Playback`      | `services/playback.ts`             | Stream sessions and the loopback proxy: one stream at a time, whichever subscription it is of                                                                                                                                                           |
| `Output`        | `services/output.ts`               | The receiver on the network that has playback, what it plays, and its progress                                                                                                                                                                          |
| `Updates`       | `services/updates.ts`              | The release channel, checks, downloads and the install                                                                                                                                                                                                  |
| `Guide`         | `@mrstreamer/core/guide/service`   | Each subscription's programme guide                                                                                                                                                                                                                     |
| `ViewingRecord` | `@mrstreamer/core/viewing/service` | Favourites, watch history, title progress and episode marks                                                                                                                                                                                             |
| `Watchlist`     | `services/watchlist.ts`            | Movies and whole series saved to watch later                                                                                                                                                                                                            |
| `Licences`      | `services/licences.ts`             | The app's and third-party notices for About                                                                                                                                                                                                             |

A service is a `Context.Service` class with a `layer`, and reaches the others through the context rather than callbacks. Services whose rules run without the platform live in `packages/core` and ask for what they need through ports, services of their own that the app supplies: the guide's are `GuideSource` (the saved subscriptions, each with its download and where its document is kept), `GuideCatalogue` (a subscription's guide ids) and `GuideStore` (the saved documents, `platform/guide-store.ts`). The others live in the app. Every expected failure is a `Failed` from `@mrstreamer/core/failure`, carrying the `AppError` the UI shows; a provider adapter's `AppFailure` keeps its error, anything else counts as unexpected.

Background work, downloads and stream sessions run in their service's scope. Quitting closes open streams at once, so no ffmpeg or provider connection outlives the app, then holds the quit until the runtime is disposed of and exits (`index.ts`); a second quit meanwhile changes nothing. Disposing also ends what a receiver plays and lets go of it, each adapter within its own bound: 1.5 s for a Cast device to confirm, and the time the AirPlay helper takes to exit before it is killed. Disposing takes a few hundredths of a second, and up to 2 s while the movie and series lists are being saved. An update's restart goes through the same path: electron-updater starts the installer, or on macOS hands the update to Squirrel, before it asks the app to quit, so the wait only delays the exit the installer waits for. Disposing stops the calls still running; they answer nobody and aren't logged. Tests build the same layers with the fake provider; `apps/desktop/test/support.ts` makes a runtime per test and calls services with promises, and guide tests move a `TestClock` instead of waiting.

## Diagnostics

`@mrstreamer/core/diagnostics` defines what the app notes about its own work, as a typed union: steps with their duration and outcome (start, login, catalogue, movie and series list and guide downloads, a title's details, update checks, downloads and installs), each stream the proxy served (direct, converted, repaired or refused, and how long it took to start), each movie or episode run (whether the picture and sound were copied or converted), what an update source answered when a check failed (the HTTP status and GitHub's rate-limit headers), and failed IPC calls. Entries hold only names, numbers and failure kinds, so an address, login or channel name can't reach them; `diagnosed(step)` times an Effect and records how it ended. `Diagnostics` is a context reference that records nothing by default. The app provides `platform/diagnostics-log.ts`, which appends JSON lines to `diagnostics.log` and starts a new file at 512 KB, keeping the one before. Disposing of the runtime waits for lines still being written, and quitting waits for that (see [Effect services](#effect-services)), so the log holds a session's last lines when the app exits. Nothing is sent anywhere.

## Viewing record

Favourites, watch history and how far movies and episodes got are events, per account: `favourite-added`, `favourite-removed` and `watched` with a channel id, `title-progress` with a title, its position and length and when that play began (`since`), `title-removed` when a title leaves Continue watching, and `series-finished` when a series' last episode was watched into its credits. `@mrstreamer/core/viewing/record` holds the rules as plain functions: `decide` turns a command into events (none when it asks for what already holds), and `apply` adds channel events to the state, favourites in the order added and the twelve most recent channels. `@mrstreamer/core/viewing/titles` holds the title rules: a checkpoint's row, when a title counts as finished (its last 5 %, at least 30 s), and Continue watching: movies past two minutes and not finished, and each series at the episode played last, finished or not, so the UI can offer the next one. The record offers up to 100 of them and the row shows 20, so the titles the UI leaves out, those for adults and those the provider no longer lists, don't push others off it. Removing a title takes every version played, by the ids of its versions, and keeps how far it got. A checkpoint brings it back only from a play begun after the removal, so the minute checkpoints of a play still going don't undo it. A finished series leaves the same way, every version played, by the ids the UI sends. `@mrstreamer/core/viewing/service` runs each command for the account of the subscription it names. Every channel and title it is given, and every one it answers with, names its subscription; the events and rows keep the provider's ids alone, under the account. Without a subscription the lists are empty, and a change fails with `no-subscription`, as does one that names a subscription that isn't saved.

`viewing.get` answers one record for every saved subscription: the favourites in the order starred, whichever subscription each is of, the channels watched by when they were watched, and Continue watching by when each title played. Nothing is stored to say so. Each entry stays in its own account's record, so removing a subscription takes its entries out of the lists and nothing else, and one whose password can't be read keeps its entries in them. The events' sequence runs through every account, so the event that gave an entry its place says where it stands among the others'. The store works that out from an account's channel events once per run, keeps it current as changes commit (`Placed` in `platform/viewing-store.ts`), and never needs it for a single account, whose lists read as they always did.

`platform/viewing-store.ts` keeps them in `mrstreamer.db` with the built-in `node:sqlite`, on the one connection `platform/database.ts` opens for it, the watchlist and locally verified files: every event in order, the state they add up to per account, one row per title and account in `titles`, with `hidden` and when the movie or series last left Continue watching (`removed_at`), and the ids of commands already done. Title events carry their details as JSON in the events table's `payload` column. A command commits its events, its id and the new state in one transaction, so a command sent again changes nothing more. `STATE_VERSION` rises when `apply` or the title rules change; the next start then rebuilds the state and the titles from every event, skipping events written by a newer version. If the database can't open, the record's calls fail and the rest of the app carries on.

Older builds share the file, as when someone returns to Stable 0.0.2: they skip event types they don't know, leave `titles` alone and insert their events without a payload, so going back and forth loses nothing. Stable 0.0.3 reads `titles` and `hidden`, and ignores `removed_at` and a checkpoint's `since`; rows it writes have no removal time, and its checkpoints count as plays begun when they were saved. It skips `series-finished` but reads the rows it hid, so a finished series stays off its Continue watching too. The UI checkpoints a title's progress every minute while it plays and at each pause, seek, track change, the end, leaving and hiding the window; never per frame. A 45-minute episode adds about 50 events.

Channel events hold stream ids, as they did before channels had several streams, and nothing stored is rewritten. The service shows the lists by channel through the `ViewingChannels` port, the library's catalogue in memory or on disk: each id becomes its channel's, once, and an id the catalogue doesn't know stays as it is. Starring a channel adds every one of its streams, so it stays a favourite while the provider lists any of them; unstarring takes out each listed stream of it; a watch records the channel's id. Builds before channels had several streams, Stable 0.0.3 among them, read the same lists and show a starred channel as its streams, losing nothing. The UI reads the lists again when the catalogue changes, as a refresh can join or split a channel's streams.

The viewer can put the favourites in another order, and no event of its own says so: an order is the same favourites, some of them removed and added again. `viewing.reorderFavourites` carries the favourites as the UI read them, of every subscription, and the channels arranged, each named with its subscription as `Viewing.favourites` names them. The service takes it only while every subscription it names is saved. It asks when the order arrives and again once their channels are found, which can take a read of a catalogue from disk, and nothing waits between that second answer and the commit: an order that names a subscription removed meanwhile is refused. Whether its stored favourites still show as that list it checks in the transaction that commits the order, against the state read there and the catalogue kept at that moment. So an order made before a favourite was starred, or before a refresh joined or split a channel's streams, fails with `favourites-changed` and writes nothing, as does a list that names a channel of another subscription, while a watch or a checkpoint in between changes nothing about it. Each channel arranged moves with every stream stored of it. Favourites the UI doesn't show, those for adults while hidden and ids the catalogue no longer has, keep their places among the others. A stream the provider dropped from a channel that still has others is such an id: nothing stored says whose it was, so it stays where it stands while its channel moves with the streams it has left. A channel shows at the first of its streams stored, so when the provider lists that stream again, a channel moved further down meanwhile shows where the stream stood, and one moved further up stays where it was put. Keeping it would take a record of which streams made up a channel when it was starred, which the events don't hold. `reordered` in `viewing/record` then keeps the start of the new order that the stored list already holds in that order and removes and adds the rest, in one pass, each in its own account's record and all in one transaction: a favourite sent to the end costs two events for each of its streams, one sent to the front two for every other stream. An order that changes nothing writes none. Nothing but those events holds the order across subscriptions: each account's record still lists its own favourites in an order of their own, which is all an older build, or the same account saved alone, reads of it. `apply` takes a command's events at once, and the rebuild an account's, so neither slows with the length of the list. Older builds read those events and the stored list as they always did, and a rebuild adds up to the same order. `ViewingChannels.lookup` takes the subscription and finds none of another's channels, so a change to one subscription's record never goes by the catalogue of another.

In Live TV's Favourites the order is a draft in the renderer until Save sends it once (`features/live/reorder.ts`). The draft holds the saved subscriptions, the favourites and the channels it was read from. It closes when the viewer leaves the list and when a subscription is added or removed, whatever it waits for, so an answer that comes later finds no draft. One being arranged closes too when the favourites or the channels change under it. The channels are the same while React Query gives the same array, which structural sharing does through every read that finds them unchanged: a refresh that changes a name or joins a stream closes the draft, and a refresh that changes nothing, new programmes or a watch don't. While the main process answers, the page takes no input. The answer is the record as it stands, which for an order sent again can be further on than that order, so the page reads the channels of the record's favourites from the main process before it shows them and never puts the draft's rows in the query cache. An answer that comes after the saved subscriptions changed, or older than the record the cache holds, changes nothing. The list stays virtualised: the row with the focus is always drawn, so it keeps the focus as it moves or scrolls out of view, and programmes are asked for by the saved order, so moving a row asks for none.

Removing a subscription keeps its record, so it returns when the account is added again, under whatever id it gets then, unless the viewer ticks the box to delete it too. Then `Roster.remove` has the record delete the account's events, state, titles and episode marks with their Undo, and what it saved to its [watchlist](#watchlist), in one transaction, with SQLite's `secure_delete` on, and checkpoints the write-ahead log: no rebuild, and no older build, finds anything of the account, and its key no longer appears in the file. `SavedSubscription.key` names the account even when its password can't be read.

The record is deleted inside the removal itself. `Subscriptions.remove` waits its turn among the storage changes, and until then the subscription is saved and takes changes as ever. At its turn it stops being saved first, then the record is deleted, then the login goes. A change checks that its subscription is saved with nothing waited for before it commits, so one that commits before the turn is deleted with the rest, and one that comes after finds no subscription and stores nothing. If the record can't be deleted, the subscription is saved again as it was, with its login and its record, and the removal fails so the viewer can try again.

The first start with the record imports the lists `preferences.json` kept before, in the transaction that sets the import marker, and only then takes them out of the file. Lists wait for the original subscription's account to import into, the only one such a file can be of, and a different account there drops them. Once the marker is set, lists found in the file again, as after running Stable 0.0.1, are removed without importing.

The UI reads `viewing.get` and sends `viewing.setFavourite`, `viewing.reorderFavourites`, `viewing.recordWatch`, `viewing.recordProgress`, `viewing.removeFromContinue`, `viewing.finishSeries`, `viewing.markEpisode` and `viewing.undoMark` with a command id it makes up; `viewing.progress` reads the rows of some movies or of a series' versions, and `viewing.episodes` how a series' episodes stand in one subscription. After each commit the main process sends `viewing.changed` with the new sequence, and the UI reads again when it holds an older one. `apps/desktop/scripts/measure-viewing.ts` measures commits, opening and a rebuild with 100,000 events, and a new order of 1,000 favourites.

### Episode marks

The viewer can mark an episode watched or unwatched by hand, from the three dots on its row in a series' details (`features/titles/EpisodeMarks.tsx`). A mark is no play. It is an event of its own, `episode-marked`, and a row of its own in `marked_episodes`, and it never touches `titles`: no `title-progress` event is written for it and no length is made up, so an older build can't take it for a play, and how far the episode's file got stays exactly as it was underneath. `episode-mark-undone` takes a mark back.

**What a mark is kept by.** The account, the series, and the episode's season and number. Never a file: a second file of the episode, another version's, or one the provider put in its place all count for it. A new mark is kept under `SeriesIdentity.key` (`seriesIdentity` in `@mrstreamer/core/viewing/marks`): `tmdb:` and its TMDB id where the lists gather the series' versions by one, so a mark holds for every version that subscription lists and for a row the provider lists the series under anew; else `id:` and the provider's id of its one version, as for a row for adults, which never joins others. Never a name. The main process works it out from the lists (`ViewingSeries`, the port `runtime.ts` fills from `OnDemand`) when the mark is made and each time it is read: the UI names a series version and never says what it belongs to.

The marks that hold for a series as the lists show it now are those kept under any of `SeriesIdentity.keys`: its key, and `id:` with the provider's id of each of its versions. Where two of them hold a mark of one episode the later one counts (`standing`). So the rules are the watchlist's (`sameTitle` in `@mrstreamer/core/ondemand/watchlist`):

- A row marked while the lists had no TMDB id for it keeps its marks when it gets one, and the versions it then joins share them.
- A mark kept under a TMDB id holds for the series with that id and no other. When its row loses the id, or is given another, the mark waits: it shows for no series, is shared with none, and holds again once a row of that subscription has the id. Providers give the id of a row they dropped to another series.
- Marks are per account, so the same series, under the same ids, at another subscription has none of them.

The UI reads `viewing.episodes` again when the lists change (`ondemand.updated`), since they say what a series is. `viewing.get` names what each marked series is kept under (`MarkedSeries.kept`), and `useContinueWatching` leaves out one whose key is none of the series' now, by the same `seriesIdentity`.

**How a mark and a play stand against each other.** By when the play began. A checkpoint carries it (`since`) and title rows keep it (`titles.since`; a row a build from before marks wrote has none and reads as begun when it was saved). It is when the viewer began the play: `title-player.ts` sets it when a title opens and keeps it through new runs, a move to a receiver, on to another one and back, and `output.openTitle` hands it to the main process, which saves a receiver's progress with it (`RemotePlayingTitle.since` gives it back to a window that takes the title up). Only opening a title again makes a new play.

Which checkpoints count is `accepted` in `@mrstreamer/core/viewing/titles`, and a checkpoint that doesn't count is written to the events and changes no row:

- One of a play older than the play the title's row holds doesn't count, for a movie as for an episode. A checkpoint that arrives late never replaces what the viewer played since. A row saved later than the checkpoint itself was saved by a clock that has been set back since, which says nothing of which play is older: that checkpoint counts, so a corrected clock never stops a title's progress from being saved.
- One of a play begun no later than the episode was last marked doesn't count, whichever version's file it is of, while that mark is kept. So the row under a mark stays what it was when the mark was made, and taking the mark back finds exactly that, whatever the play that was going saved or finished meanwhile. After the Undo that play's checkpoints count again.

`@mrstreamer/core/viewing/episodes` holds what the rows and marks add up to, as plain functions of one subscription's, and the details, Continue watching and the player all go by them:

- An episode stands as its mark says unless a play of it began after the mark (`episodeStates`). Starting the episode again afterwards takes over.
- A series goes on from what the viewer did last, a mark or a play begun after the latest mark (`continuation`): an episode played partway resumes; one marked unwatched plays from its beginning; after one watched comes the next that isn't, from its beginning, then the first earlier one that isn't, and with every numbered episode watched the first is offered again as Replay. Specials lead to specials, and once those are watched the numbered seasons go on from what the viewer did last in them.
- The player's next episode passes over watched ones and never goes back (`nextUnwatched`, see [Movies and episodes](#movies-and-episodes)).
- A play that watches an episode to its end finishes its series only when no numbered episode is left to watch, that one counted unless it was marked since the play began (`finishes`). The player asks the record as the episode reaches its credits with none left after it, and sends `viewing.finishSeries` only then: an earlier episode that isn't watched keeps the series in Continue watching, and a special never finishes the numbered seasons.

`viewing.finishSeries` carries when its play began, and a subscription that marked an episode of the series during that play or after it writes nothing for it: where the series goes on is what its marks say.

**Where a marked series goes on** takes the episodes the series lists, which the events don't hold otherwise. So `markEpisode` asks for them (`ViewingSeries.seasons`, the details the sheet just read, which `OnDemand` keeps) and for the versions the subscription lists of the series, and writes both into the event (`listing`, the seasons' and episodes' numbers, and `versions`). `marked_series` keeps them per account and key, as of the latest mark. Each time the record is read, `read` works out where every marked series that shows goes on (`goesOn`): from the rows of those versions, the marks kept under the key and under each version's id, and that listing. Nothing is stored of the answer, so it is true to the record whenever it is read: an episode that a play from before the mark watches meanwhile moves the series on, and once that leaves no numbered episode to watch the answer is null and Continue watching shows nothing for the series. It asks no provider, so Home never fetches a series to draw its row. What it can't know is a list the provider changed and the app hasn't read yet. Once it has, the record is told: whenever a series' details are read (`ondemand.details` in `main/index.ts`), `ViewingRecord.relist` compares the episodes they list, and the versions the lists give the series, with what a series last marked in that version keeps, and writes a `series-listed` event when they differ, which changes no mark and no Undo. So Home goes on by the list the sheet and the player just showed, and details that list no episode, or another version's, which has its own episodes, change nothing.

`viewing.get` answers each such series with its latest mark and that episode (`Viewing.marked`), and `useContinueWatching` puts those beside the rows played: in one subscription a play begun after the mark replaces it, one begun before it is left out, and a series with no episode to go on with shows nothing. Across subscriptions the one played or marked last stands for the title, as before. Pressing the tile works the continuation out from the details and `viewing.episodes`, as the sheet does. Taking a series out of Continue watching hides its marks' entry too, until the next mark: `title-removed` and `series-finished` name an episode of the version, a series only marked is named by an episode marked in it, and every marked series that listed the version when it was last marked goes out with it (`left`), keeping when (`left_at`), so what a play from before the removal saves stays out of the row as it does for a played series.

**Undo.** A marked series keeps what its latest mark replaced (`marked_series.undo`): the episode's mark before it, if any, and whether the series was out of Continue watching. `viewing.undoMark` names the mark by its `revision`, the sequence of its event, and puts exactly that back; the episode's row was never changed under the mark, so the Resume point is the one from before it. In the transaction that does so it refuses with `mark-changed` unless that mark is still the series' latest and no row of any of the series' versions began after it (`undoable`). `marked_series.changed` holds the sequence of the key's last mark or Undo, and only the key changed last can hold the mark to take back, so a later mark ends an earlier one's Undo also when the lists moved the series to another key between them, and an Undo is never taken twice. Leaving Continue watching ends it too, as does a mark an Undo put back. `viewing.episodes` answers which mark that still is (`SeriesViewing.undoable`), by the same check, so the sheet stops offering an Undo the record would refuse. The mark, its event, the projection and what it replaced commit together or not at all, and a command sent again finds its id and changes nothing.

`@mrstreamer/core/viewing/marks` holds what an event does to a series' marks (`marked`, `left`), `series-listed` among them. `project` in the store applies a title or mark event to an account's rows and marks, and the store runs that one function on the tables when a change commits and on memory when it rebuilds, so both add up to the same. `STATE_VERSION` didn't rise for marks: nothing stored before them reads differently.

When the record can't be read, nothing is shown as unwatched on a guess. `viewing.episodes` fails, the sheet says so with Try again, names no episode to go on with and offers no marks, and keeps what it read before when only a later read fails. The player offers and opens a next episode on the record's answer alone (`refreshNext`): it asks as an episode opens, as the record changes, as the episode ends and once more before the next one opens. Only its latest question counts. The answer to an earlier one is dropped, whichever of the two arrives first, and while the record doesn't answer the latest it counts down to nothing and opens nothing.

Older builds never look at the two tables. Going back to one and returning keeps every mark; a play that build saves meanwhile reads as begun when it was saved, so it takes over from an earlier mark of that episode, as a play here would. Its rebuild deletes `state` and `titles` and nothing else. When such a build removes a subscription with the box ticked, it erases the events and leaves the account's rows of these two tables, with the account's key. No mark is kept without the events that made it: this build deletes them at its next start, as an erase does, so the key is gone from the file then.

## Watchlist

Movies and whole series the viewer saved to watch later. `services/watchlist.ts` (`Watchlist`) answers `watchlist.list`, a page of the entries with the title each is in the lists now, `watchlist.saved`, the entry a title is saved as, and `watchlist.save` and `watchlist.remove`. A change answers once it is stored, and `watchlist.changed` tells the UI after. Nothing here is the viewing record's: no event, row or rule of that record knows of it, so playing, finishing or leaving Continue watching changes no entry, and saving changes nothing of how far a title got. The calls take a movie or a series, by one of its versions, so an episode can't be saved.

### What an entry is

Each account keeps its own record of a title it saved. A record has an id of its own, made up when it is saved, the time it was saved, the title's kind, its provider's ids of the versions that subscription lists, its TMDB id when the lists give one, and a name, a year and whether it is for adults, to show when the provider lists the title no more. It keeps nothing else: no address, no artwork, no details. The UI names a title by one of its versions and sends nothing more. The main process takes the title from the lists and works the rest out for each subscription (`factsOf`), and asks no provider anything.

The watchlist the viewer sees is made of every saved subscription's records together. An entry is what they saved of one title: a film two subscriptions list under one TMDB id is one title in the lists (see [Titles and versions](#titles-and-versions)), and the records both hold of it are one entry (`sameEntry`, `entriesOf`). The same proof that joins the versions joins the records, and nothing else does. Two providers number alike, so a record without that TMDB id, or of a row for adults, is an entry of its own, whatever another subscription saved under the same id or the same name. The record saved first names its entry, as an `OwnedId`, and gives it the time it was saved. Where two records have the same time, the one written first is the one saved first (`savedFirst`): the store reads each record's place in that order from its row's `rowid`.

`@mrstreamer/core/ondemand/watchlist` holds the rules as plain functions. `sameTitle` says when a record and a title in its own subscription's lists are the same movie or series:

- A record with a TMDB id is the title with that id and no other. Where the lists gather both by the id, the id is enough. Another language or quality, a new name, another order and a provider id the title never had change nothing.
- A provider id the record holds proves nothing against that. Providers give the id of a row they dropped to another film, so a row that now carries another TMDB id, or none, is not the saved title. The record finds nothing and keeps what it had, saving the newcomer makes a record of its own, and the first is itself again once the lists show its TMDB id.
- A row for adults never joins others by its TMDB id, so the id alone doesn't say which row a record is. There the record must hold the row's provider id as well. That covers a saved title the provider starts marking for adults, and a saved row for adults the provider stops marking. It is also why a film for adults two subscriptions list is two titles and, saved from both, two entries.
- A record without a TMDB id is the title that has one of its versions, in its own subscription. A title TMDB doesn't name is known by the provider's id of its row and by nothing else. Such a record follows that id, also when the provider gives it to another film, because nothing in the lists tells the two apart.
- Names and years join nothing, so two titles called the same stay two.

A record gains a TMDB id once its subscription's lists have one for its row, and never loses it. A row that lost the id is no longer taken for the record. Records of one account that turn out to be one title, as two rows saved before the provider gave them one TMDB id, become the one saved first, with its id and its time (`settled`). Records of two accounts that turn out to be one film stay a record each and show as one entry from then on, named by the one saved first.

### Saving and removing

Saving a title saves it for every subscription that lists a version of it now. Nobody is asked which. `Watchlist.save` takes the title from the lists, with the versions of every subscription, and `WatchlistStore.save` writes a record for each of those accounts in one transaction: all of them or none. An account that holds a record already keeps it, with its id and its time, and a new record takes the time the entry was saved first, so the entry keeps its place whichever subscription goes later. It is written after the records there already, so it stands behind them and the entry keeps its id too, whichever of the subscriptions comes first in Settings. Saving a title that every one of them holds a record of changes nothing, and two saves at once make one entry.

A subscription added later that lists the title too plays it from the same entry, through the menu beside Play. It is given no record by itself: bringing records in line with the lists never makes one. So `WatchlistEntry.sources` names the subscriptions the title was saved from, and removing one of those without deleting its data takes the entry out of the list only when no other source holds it.

`watchlist.remove` names an entry by the record saved first. The store finds every record of the saved subscriptions that is that entry and deletes them in one transaction, also a record whose own provider lists the title no more. A record that is no other's entry goes alone, so nothing else that shares its name or its provider id is touched. One already gone changes nothing. What an account kept whose subscription isn't saved stays as it is.

### Where it is kept

`platform/watchlist-store.ts` keeps two tables in `mrstreamer.db`: `watchlist`, one row per record and account, and `watchlist_versions`, one row per version, which names the record it belongs to. A unique index holds one record per account, kind and TMDB id among the titles the lists gather by it, which leaves out rows for adults. Two records of an account can hold one provider id, as when the provider gave a saved title's id to another title and the viewer saved that one too. The index on the provider id finds the records, and `sameTitle` says which of them a title is. Like the viewing record, they keep the provider's ids under the account's key and name no subscription. The service says whose an account's records are.

Every change is one transaction. A failure rolls everything back: nothing is half saved, for one account or for several, the call fails, and the UI offers the same action again.

`platform/database.ts` opens the file once for both stores. Each makes and reads its own tables only. The viewing record's rebuild deletes `state` and `titles` and nothing else, here and in every build before, so a change to its rules, or an older build working on the file, leaves the watchlist as it is. A build from before the watchlist never looks at these tables. Going back to one loses nothing, with one limit: when such a build removes a subscription with the box ticked, it erases the viewing record alone, and the account's watchlist rows, with the account's key, stay in the file until this build erases that account.

### Which title an entry is now

The lists say, each time the watchlist is read, and nothing of that is stored. The main process reads the records of the saved subscriptions, one indexed read each, and the catalogue worker answers a page of the entries they make (`saved`), from the one catalogue it keeps for every list. `titleOf` finds a record's title by its TMDB id in an index of the gathered titles (`byTmdbId`, built when first asked for), whichever subscription lists it now, else by the first of its versions whose row its own subscription still lists as it (`byId`, by `OwnedId`). An entry is the title any of its records finds. The worker also leaves out titles for adults while the viewer hides them, orders the rest by the time saved or by the name each shows, and counts them. One place decides what shows, so the count and the grid never disagree, and a title's name is the one every other list gives it, TMDB's included.

An entry the lists hold no title for stays, with `title` null and what was kept of it. `WatchlistEntry.listed` says whether the lists of every subscription that saved it were there to look in. Without one of them, as after a first fetch that failed or for a subscription whose password is needed again, nothing says its provider dropped the title, and the entry isn't called unavailable. A refresh that fails keeps the lists, so it changes no entry. For a title no provider lists, the worker adds TMDB's backdrop when its metadata has one. A provider's own artwork address is never kept.

After every fetch of a subscription's lists, and before a read or a change when this run only read them from disk, the service brings that account's records in line with them (`align`, `adopt`): each record whose title its subscription lists takes its name, year, versions and adult mark as they are now, gains a TMDB id where the row got one, and joins the record saved first where two are one title. Doing so after every fetch is what follows a title from one fetch to the next: a row that gets a TMDB id today and is dropped tomorrow is still found by that id. A title only another subscription lists now leaves the record as it was. Records that are as the lists describe them aren't written again. When it fails, the records stay as they were, reads carry on, and the next call tries again.

Measured on one machine with a catalogue of 53,000 movies: the TMDB index takes about 25 ms in the worker, once, the first time the watchlist is read after the lists load, and indexing the catalogue costs nothing more than before. With 100 titles saved, a page takes 0.1 ms in the worker, reading the records 0.8 ms and bringing them in line 4 ms. With 1,000, a page takes 2 ms, reading the records 6 ms, and bringing them in line 22 ms when nothing changed and 41 ms when every title was renamed. Those were taken with one subscription. With two of 53,000 movies each, six in ten of them the same films, on a busier machine: the TMDB index took 36 ms, once, and working out the entries and their titles took 1.4 ms for 100 saved titles, 185 records, and 4.7 ms for 1,000, 1,545 records. The worker reads the index it already keeps for every list, so the watchlist indexes nothing again, and saving a title is one lookup there and one transaction, with no request to a provider, to TMDB, or for a title's details.

### Whose an entry is

Every call names a subscription, and one that isn't saved fails with `no-subscription`. A save takes its title from the lists, which can mean waiting for the worker or for a first fetch. So the service notes the saved subscriptions with their logins before it asks (`SavedSubscription.revision`), and reads them again as the last thing before it stores, with nothing waiting in between. Every subscription the lists gave a version of has to be saved still, with the login it had (`sameSource`). When one went or had its password entered again meanwhile, the save fails and stores nothing, for that subscription or for the others. A removal waits for nothing: it deletes from the accounts of the subscriptions saved as it arrives. The same check guards bringing records in line with new lists. A record is written under its account's key and deleted by it, so no change reaches another account's records.

Removing a subscription keeps what its account saved, which returns when the account is added again, under whatever id the subscription has then. Ticking the box deletes it: `Roster.remove` has `viewing.erase` delete the account's rows of both tables in the transaction that erases its viewing record, once the subscription is saved no more (see [Viewing record](#viewing-record)). A save under way for it then stores nothing. Either way the other subscriptions keep their records, so an entry two of them saved stays for the one that is left.

### In the window

Watchlist is a page of its own in the top bar, while a saved subscription has movies and series (`features/watchlist/WatchlistPage.tsx`). It draws its tiles in the collections' `Grid`, with the same keys, and reads pages of 120 as the grid asks. Home's row reads the same first page. Nothing on either asks for a title's details: those load when its sheet opens, where the menu beside Play offers each subscription's versions. A tile says which subscription its title is from only where another's reads the same and isn't it (`useSourceOf`), as every poster does. A tile whose title the lists don't have opens a short sheet instead (`SavedSheet.tsx`), with what was kept and Remove. Beside other subscriptions the sheet names those the title was saved from. When the lists of one couldn't be fetched again, the page says so in a line with Try again, which names that subscription when there are several.

Save sits beside Play in a title's details (`SaveButton.tsx`, `useSaveToggle` in `lib/watchlist.ts`). It goes by the title from the lists (`ondemand.titles`), which answers without the network, so it works while the provider's details are on their way. The button changes what it says once the main process answered that the change is stored. Until then it keeps its words and takes no second press, and a failure shows under it. It is never disabled while a change is stored, so it keeps the keyboard's focus. A tile's cross and the sheet's Remove take no second press either (`useRemoveSaved`). React hears that a change began a moment after it did, so each of the three also keeps a ref, set as the press lands and cleared when the change ended, stored or not: a second press in that moment would otherwise start a second change, and the window would show that one's answer instead of the first's.

The window reads the watchlist again on `watchlist.changed` and on `ondemand.updated`, since the lists say which title an entry is, when a subscription is added or removed, and when Settings changes the language or whether titles for adults show. That last one drops what was read before, first and with nothing waited for, so a title now hidden doesn't stay on screen while the new answer comes. The sheet of a dropped title holds its entry as it was read (`savedEntry` in the UI store) and stays open under Settings, so hiding titles for adults closes it as the viewer unticks the box, before the main process answers. Removing a subscription the title was saved from closes it too.

## Programme guide

`@mrstreamer/core/guide/service` downloads each subscription's XMLTV (`xmltv.php` on Xtream panels, the document a playlist's header names) and keeps it separate from the catalogue and playback: listings are empty until a guide loads, and nothing waits for one. Each subscription has a guide of its own, an index on disk in its own folder, and every subscription reads the XMLTV sources the viewer adds after it (see [Guides from other addresses](#guides-from-other-addresses)). A channel's guide ids are matched within its own subscription alone: two providers' guide ids are as unrelated as their channel ids. `guide.listings` answers each channel from its subscription's guide, and `guide.search` searches all of them and cuts the answer at fifty after putting them together. `@mrstreamer/core/guide/document` unpacks a document that is gzip by its first two bytes, wherever the sender split them and whatever its address or its server calls it, and hands it on in pieces of 64 KB. `@mrstreamer/core/guide/xmltv` reads it chunk by chunk. It searches the bytes and decodes one channel or programme at a time, so the strings it keeps don't hold on to the chunks they came in. It reads text and nothing else: a DOCTYPE is passed over and the only references it knows are XML's five and numbered characters, so no document makes it fetch or read anything.

A download runs in two steps, which `GuideStatus.processing` tells as they go: `downloading`, the document saved as it arrives with the bytes so far and the size when the server says, then `reading`, the programmes indexed so far and since when; then `ready`, with the catalogue's channels it covers, its programmes, when they run until and when it was downloaded; `failed`, with the reason, since when, and when the download still in use arrived; or `empty` while there is no guide. Each state holds all a Settings row needs to show it: Settings > Guides shows a source's as it goes, and a subscription's Guide row says why its own failed. Each step is published on `guide.updated` at once, its progress at most four times a second, and Settings reads the status again. `@mrstreamer/core/guide/index-file` writes each document into a SQLite file of its own (`buildGuideIndex`), in a worker thread per document (`main/guide/index-worker.ts`, started by `platform/guide-indexer.ts` with a bounded heap): on the main process of a busy machine, single SQLite writes of a few thousand programmes took up to 600 ms, and the 1.2-million-programme guide is half a minute of reading. Programmes are kept by guide channel and start, in time order and without overlaps: a programme without an end runs until the next one, overlaps are cut, and a start listed twice counts once, as the document first lists it, also an entry without an end before one with an end (releases before 0.0.13 kept the later one then). Titles are kept once each, folded for search, under a (title, start) index. What an index keeps is bounded where it is read (`GUIDE_KEPT` in `@mrstreamer/core/guide/limits`): a title of 300 characters and a description of 2,000, cut where a character ends, a channel name of 128 characters, no channel whose id is longer than 128, and no programme shorter than a minute once laid out. So a row is a few kilobytes at most and a channel's day 1,440 programmes at most, and whatever reads the index reads little by construction. The build writes each programme as it reads it, a transaction every 5,000 programmes or 8 MB, and remembers titles up to 100,000 or 8 MB; a string it keeps is a copy, never part of the element it was read from. The guide in use keeps answering throughout, and the new index replaces it only once whole.

Two rules keep the files whole. Every file of a guide has holders, kept in one registry per service (`@mrstreamer/core/guide/files`): the guide loaded from it, a read under way, a build reading the past from it, the download or build writing it, and what is kept naming it (`guide.json`, `sources.json`). An index is open while one of its holders reads it, and a file goes only once nothing holds it; nothing else closes or deletes one. Work that hands what it made on, a download kept as the guide, claims it for the next holder in the same step and lets go of its own claim after, so stopping it never closes or removes what it handed on. A download and the index built from it are claimed together and let go of together however the work ends, also when it is stopped between indexing and handing on. A read claims the index it began with before it waits for the catalogue, until all it read is read, also a search's answer from the worker. A build reading the past claims that file from when it names it until it is done, and indexing a document an older release kept claims that document the same way, and a stopped build waits for its worker to end before it lets go; carry-over opens the file read-only, so one that is gone fails the build rather than bring nothing. The second rule: whatever decides which guide is current, a download or a reindex kept, a source added, moved or removed, a mapping, a failure noted, `forget`, runs in a turn, a subscription's own or the one turn of the sources' list, one at a time and to its end once begun, and checks there whether it still applies. A subscription's turn may wait for the sources' turn, never the other way. Once a run has read every record of the guides, each subscription's and the sources', it sweeps each folder once, in its turn and in the background, of the indexes and downloads the registry doesn't know, asking just before each goes and leaving the `.part` a build writes into while the registry holds the index it becomes: what a run before left behind. A record that is there but can't be read, or a file the store can't look at, isn't taken for none: it keeps everything for the rest of the run, with no sweep and nothing let go of, and is read again at the next start.

The main process opens an index read-only and keeps only its channels in memory, about 200 bytes each and under two kilobytes at most. Now and next, a schedule and `guide.range`, a grid's page of channels over a stretch of time, read a channel's rows by its key. Live reads, now and next, schedules, searches and the channels covered, show a channel, of the first of its guides in order with programmes left at the time read for one of its guide ids, the first such id; a channel whose guide ids only keep the past isn't covered, and a later guide never patches an earlier one's channel. A schedule and `guide.range` pick that guide as listings do, at the time now, whatever stretch they read, past or future: pages of a grid side by side never read two guides for one channel. Either reads the whole stretch from the one guide picked, never a patchwork, and each slot names it; a guide that took over a channel shows only the past it kept itself. Searches run in a worker thread of their own (`main/guide/search-worker.ts`, started by `platform/guide-searcher.ts`), which opens each guide's index read-only for each search: a search may read hundreds of thousands of programmes in one SQLite statement, which no slicing on the main process could interrupt. The main process works out which of the guide's channels a catalogue shows, sends their keys, and reads the answer. The worker reads the titles that match, 10,000 titles at a time, then their programmes in stretches of time from what is on now, and the few over six hours long, which have an index of their own, so one four-day event doesn't make every search read four days back; a search every title matches holds a page of them, never all. A search the worker hasn't answered after 30 seconds is given up and the worker ended, as when the search is stopped, its subscription forgotten or the app quits; the next search starts another worker. A list's search answers per channel; the main process works out the channels' keys before it and maps the answer back after it in slices of about 8 ms, and the worker packs the answer into a few arrays and one string, so taking it in builds nothing per channel. `guide.schedule` reads a channel over the `from` and `until` it is asked for, the start and end of the viewer's day, so what aired that day comes along for catch-up: at most `GUIDE_SCHEDULE.most` programmes, which holds a day of 26 hours of one-minute programmes, the longest a clock that goes back two hours makes, a whole day with what a search of it finds; and where the day holds fewer than `GUIDE_SCHEDULE.atLeast` still to come, or, once it has begun, fewer that aired, a few more past its end or from before its start. `guide.range` answers slots without descriptions, a few hundred a channel at most over its 12 hours, reads a guide channel that several channels show once, and lets other work in between channels. Each slot names the guide channel it is of (`guide`), which a channel whose guide ids name several can tell apart; `guide.programme` reads one programme's description by the channel, that `guide` and the start, and answers null unless that guide channel supplies the channel now, as every other read picks it. Since the guide that supplies a channel changes with time alone when its last programme ends, the service checks the time each minute, and the app when the computer wakes or is unlocked (`Guide.checkTime`): it reads the guides as they stood at the last check, and tells the window once when one of those ends has passed since, or the clock went back or jumped forward more than two minutes, so a grid's pages and details it keeps are read again within a minute of a handover. An end that passes while the guides are read counts at that check. A check keeps each subscription's next such end while its guides and channels are the same and it hasn't come, so a quiet minute reads next to nothing; one that works ends out again does it in slices of about 8 ms over every subscription together, and lets the event loop run between subscriptions. How many of a catalogue's channels a guide covers, and which catalogue channel a search names for each guide channel, are worked out in slices of about 8 ms the first time, once however many ask meanwhile, and kept while the same channels have programmes to come. A search's first fifty take in programmes that start as late as the fiftieth, so of those that start together, the one on the channel the file keys first is found, whatever page of titles it is on. Ended programmes are kept for the subscription's archive window (`GuideSubscription.archive`, seven days until providers say how far back their catch-up reaches). The next download of the same source brings along the past its document no longer lists, on the channels it still has, cut where the document's first programme there begins; what falls out of the window goes, also what only falls out once cut. A channel the new document no longer has programmes for goes, past and all.

`Provider.liveGuide` answers with the document or with `none`, a subscription without a guide, which only a playlist is. That is an answer, never a failure: the service drops a guide it had for that subscription, from memory and from disk, says `none` in its status, and from then on its own checks leave the subscription alone, so nothing is fetched or logged every quarter of an hour. `guide.refresh` names a subscription and asks again, and a guide found then loads as any other. The answer isn't kept across a restart: until a subscription has answered, its status says `unknown`, and Settings shows "not loaded yet" rather than claim a playlist has no guide. `guide.status` answers one status per subscription, and none ever holds the guide's address.

A download replaces the guide only when it completes and lists programmes; otherwise the last guide stays, also when the playlist itself can't be read. The main process downloads after a subscription is added or repaired and at startup; the service itself checks every 15 minutes and downloads each guide that is six hours old, two at a time, and each source that is. A subscription that is removed, or whose login changed, takes only its own guide with it (`Guide.forget`): its download in progress stops, and a load or download that finishes afterwards changes nothing, while the others' guides stay loaded. A download commits to disk only while its subscription still stands with the login it began under. The lookups over a catalogue's channels are plain functions in `@mrstreamer/core/guide/programmes`. A download that fails is noted with the time of the first failure since the last one that worked, and `guide.status` says both until a download works again.

### Guides from other addresses

The viewer adds XMLTV guides of their own in Settings > Guides (`features/settings/GuidesSection.tsx`): one list in their order, which every subscription reads after its own guide. `Guide.addSource` seals the address, keeps it in `guides/sources.json` at once and answers the source's status; its download and indexing follow in the background, once for every subscription, its index beside `sources.json`. `Guide.moveSource` moves one a place earlier or later, `Guide.removeSource` stops its download and drops it with its index, and `Guide.refreshSource` downloads one now, joining a download under way. `guide.sources` answers each with its id, its origin, whether the keychain still opens it and the same `processing` a subscription's guide has, where `ready` counts the channels it supplies over every subscription. Each change is told on `guide.updated`.

A subscription's guides are its own, then the sources in order (`Guides` in `@mrstreamer/core/guide/programmes`), each guide channel named by its guide and its id (`guideRef`). For each channel the first guide with programmes still to come for one of its guide ids supplies the whole channel; a mapping by hand comes before the order for its channel. `guide.status` says per subscription how many channels each guide supplies, its own first (`supplied`), which its Guide row in Settings > Subscriptions shows with a link to Settings > Guides. A search reads every guide in its worker and puts the answers together before it cuts them at fifty.

A source that fails keeps its last download that worked and its place: its status says `failed`, why, since when and when the download still in use arrived, and `sources.json` keeps the failure, so it shows after a restart. Nothing asks a provider in its place.

A source must be whole XMLTV with something still to come (`buildGuideIndex` with `strict`): it fails as `not-xmltv` unless `<tv>` is its one outermost element, `incomplete` when that never closes with `</tv>` or its gzip is cut or damaged, `empty` without programmes and `ended` when all of them have. The reader tells those two tags from text as XML does: what a comment or a CDATA section holds is never one of them, and neither is `</tvirus>`. An own guide is taken as its provider sends it, as it always was, and fails only without programmes.

The address can hold a key. `@mrstreamer/core/guide/address` makes what was typed whole, an address without a scheme meaning https, and refuses anything that isn't http or https or carries a user and password. It is sealed with `safeStorage` in `sources.json` beside its origin and part of its SHA-256, which tells the same address from another without holding either, so the same address added again is the same source. Only the origin ever reaches the window, a log or the diagnostics: `guide.sources` and `guide.status` answer it and nothing else of the address, and the field that takes one starts empty again once it is added. `providers/xmltv.ts` requests it as the app, with a User-Agent and an Accept header and no login. It follows five redirects at most and never from https to http, gives the answer, every redirect before it and the document fifteen minutes together, and names no more than an origin in what it fails with. A keychain that no longer opens the address leaves what was downloaded as it is: the status says `locked`, nothing refreshes, and the same address added again takes its place again, with its mappings.

`platform/guide-store.ts` keeps each guide as an index (`guide-index.<id>.sqlite`) named by one small record: the own guide's by `guide.json`, with its account and download time, and the sources' by `guides/sources.json`. Releases before 0.0.13 kept the documents themselves, `guide.xml` and `guide-external.<id>.xml`, and a subscription could take an XMLTV address of the viewer's own in place of its own guide, kept in its `guide-source.json`. The first time a subscription's guide is read, and before the sources are answered, such an address moves to the sources, and the move only adds. The same address of several subscriptions becomes one source, which reads one download of theirs: the newest, then the larger, then the first by name, whichever subscription is read first. That one is copied to `guides`, a link where the disk allows, and claimed there before `sources.json` names it, with where it came from (`movedFrom`). Only then does the subscription's `guide-source.json` name that source, beside the address and its file, which stay, and the mappings made against it name it too. Every subscription keeps the address and its own file, unread, until the source's first download of its own, which lets go of them through the registry; a mapping to a guide channel only another download listed counts as unresolved until then. A source a move brought downloads at the next refresh, however recent what it brought, so that is one download away. A download of its own replaced in a run that keeps everything stays held until the run ends, and the next start that reads everything sweeps it and lets go of the addresses. A step that fails, or a run cut short, leaves what was there for the next start, which moves it again; an address that couldn't move this run is read where it is meanwhile, an XMLTV one indexed beside it in the background into a file nothing names. The service indexes a document an older release kept in the background, as it does a download, and names the index in its place; lookups answer empty meanwhile, and a refresh waits for it. Going back to 0.0.12 finds no `guide.xml`, so it downloads the own guide again, and a `guide-source.json` that still has the address gives it that guide back, one without its own guide, with the mappings it finds there. The store writes into a subscription's folder and never makes one, so a write that arrives late for a subscription that went fails instead of bringing its folder back.

Every change to what is set goes through one function in the service, one at a time. One to a subscription applies only while it is saved with the login the change began under, and one to a source only while the source is listed, checked when the change's turn at the files comes, and it can't be stopped halfway. So a download or a mapping that finishes after a removal or a password entered again writes nothing. A mapping also reads the channels and the guides in that turn, so it maps nothing to a channel the provider, or a guide channel its guide, stopped listing while it waited. `Guide.forget` raises that subscription's count first, stops its work, then takes its own turn and erases, so nothing comes after it. A new name leaves the login's revision as it is, and so the guide.

### Channels mapped by hand

A channel shows the programmes of the guide channel its own trusted guide id names, when the guide has that id exactly. `guide.map` gives it the guide channel the viewer picks instead, by its guide and its exact id (`guideRef`), and null takes the mapping away again. Nothing is matched by name anywhere. `mappedChannels` lays the mappings over a catalogue's guide ids both ways: a mapped channel reads the guide channel it was mapped to and no other, before the guides' order and also when its guide doesn't list that one, and a guide id's channels are those that name it themselves and aren't mapped elsewhere, with those mapped to it, in catalogue order. Every lookup reads that one view, so now and next, a schedule, the count of covered channels, `guide.search` and `guide.searchList` agree.

A mapping is kept in `guide-source.json` under the channel's id as it was then, with the guide channel's source and the channel's name, and finds the channel by any of its streams' ids, as the catalogue does. It holds through a restart and a new channel list. One whose guide channel its guide no longer lists, or whose channel the provider no longer lists, shows no programmes and counts as `unresolved` in the status; it is never pointed at another. One whose source was removed counts as `unresolved` too, and its channel reads the guides in order again until the viewer maps it again or takes it away.

Settings maps channels in a sheet (`features/settings/GuideMap.tsx`). `guide.mapChannels` answers a page of the catalogue's channels as the lists show them: those without programmes, those mapped by hand, with any the provider no longer lists last, or all, cut down by name or number. `guide.mapOptions` answers a page of the guides' channels by name, the own guide's and then each source's, each with its guide, its id and whether it has programmes, and no programme. Both lists read 120 rows at a time and draw only those in view. A page names the guides in use when its read began, and `guide.map` refuses a choice made from others, so one from a page read while a guide changed is refused too. A mapping changes which channels a filter shows, and so where each page begins, so the sheet reads its pages of them again after every one, and on `guide.updated` as every guide query does. The names searched are folded once: the catalogue's with the catalogue, and a guide's channels as they are read, since folding thousands of names at once takes longer than a search may hold the process.

### What a guide may hold

Every guide, own or not, is read under the limits in `@mrstreamer/core/guide/limits`, and one past any of them is refused whole with `too-large`, never cut: 2 GiB unpacked, 1 MiB for one channel or programme, and 50,000 guide channels, whose names are what an index keeps in memory. How many programmes a guide lists has no limit of its own: they stay on disk. The limits are set against the largest real guide the [guide budgets](testing.md#guide-budgets) are measured with: a US guide of 512 MiB unpacked, 82 MB packed, 12,994 channels and 1.18 million programmes over ten days. The size limit counts bytes as they are unpacked, and a download as it arrives, so a small gzip can't unpack past it, and an element that never closes stops at its limit.

The UI asks `guide.listings` for now and next per channel, `guide.schedule` for one channel's day (`GUIDE_SCHEDULE`), `guide.range` for a page of a grid (`GUIDE_RANGE`: up to 30 channels by 12 hours), `guide.programme` for one programme's description, `guide.search` for programme titles across the catalogue and `guide.searchList` for those of one list's channels. Settings asks `guide.status` for how many of a catalogue's channels each of its guides supplies and when its own was downloaded, `guide.refresh` downloads one now, and `guide.sources` answers Settings > Guides. Lists ask for listings in pages of 40 as rows come into view, and again each minute. `apps/desktop/scripts/measure-guide.ts` measures download, indexing, stalls, lookups and memory against the [guide budgets](testing.md#guide-budgets).

Live TV searches the list it shows from the field beside the list's name (`useListSearch` in `features/live/lists.ts`). The renderer holds the list's channels, so it finds names itself: the name shown, the provider's and each stream's, folded as `@mrstreamer/core/text` folds them. For programmes it calls `guide.searchList`, which names the list as `library.channels` does. The main process reads that list from the library as Live TV shows it, and `searchChannelsAt` answers per channel whether the programme on now has every word in its title and which later one is the first that does, before `until`, the end of the viewer's day. `guide.search` can't stand in for it: it returns the first fifty programmes of the whole catalogue, each on the first channel that shows its guide id, so cutting that answer down to a list misses what the fifty left out and every other channel sharing an id. `searchChannelsAt` searches every channel of the list, answers one entry per channel at most, without descriptions, and gives channels that share a guide id the same answer. The rows change once that answer is in, names and programmes together, 120 ms after typing pauses, and nothing is asked of the provider. The field's text is the page's own state: another list, another account and a restart start without it. Each list, and each search of it, gets a `ChannelTable` of its own, because a virtualiser kept across them moves the next list by what it measured of the one before.

## Views and the picture

The window shows a page, Home, Live TV, Movies, Series or Watchlist. A title's details open in a sheet over the page, and so does what was kept of a saved title the lists no longer have; Watch, for a channel, and a playing movie or episode open over everything. The page stays laid out underneath, hidden and `inert`, so leaving any of them finds it scrolled where it was and a key or Tab never reaches it meanwhile.

There is one `<video>` element, created by the live player controller (`player/player.ts`). Home's backdrop, the guide's preview, Watch and a playing title each render a `Picture` (`player/Picture.tsx`); the active one holds the element, moved with `moveBefore` so it keeps playing. Moving between views never reopens the stream or opens a second provider connection. The packaged-app test checks this through the fake provider's stream count.

The mini player is the same window, shrunk. `app/mini-player.ts` asks the main process (`window.setMiniPlayer`, `main/mini-player.ts`) to remember the window's bounds and whether it was maximized, then to give it a 16:9 size in the corner of its screen, or where the viewer left it last, always on top at the `floating` level, and on macOS on every space, full-screen ones included, without its traffic lights; Windows and Linux get a lower window-buttons strip. Going back restores the bounds, the maximized state and, from the renderer, full screen. The page's request for full screen is granted within a millisecond, while macOS takes over half a second more to get the window there and changes its size at the start of the way. So the way back is done only once the main process says the window fills the screen (`window.fullScreen`), or after two seconds without its word. A way in asked for meanwhile lets the window arrive first, since the main process can't tell a window on its way into full screen from one that is not. A way back that a way in overtakes asks for no full screen, and leaves that to the next. Watch and a playing title lay themselves out smaller while it is on, with the same `Picture`, so the stream, its position, tracks, speed and volume carry on. Leaving the view, or opening search or Settings, puts the window back. Electron documents that macOS hides the window and the Dock icon for a moment whenever `setVisibleOnAllWorkspaces` changes, and that always on top doesn't work under Wayland; `window.miniPlayerAvailable` says false there, from the Ozone platform or the session type, and the button doesn't show.

Sound follows the view: Watch and a playing title play at the viewer's volume, and pages keep the stream muted unless the speaker is pressed (`audible` in the player state). Home and Live TV start a muted preview of the last channel; Movies, Series and the Watchlist stop it, and coming back starts it again, muted. A preview never reconnects after a failure, so a connection another device holds isn't fought over, and it stops while the window is hidden and restarts when it shows. Stop in Watch keeps previews from starting it again.

`player/media-session.ts` fills `navigator.mediaSession`, which Chromium hands to macOS's Now Playing, Windows' media overlay and Linux's MPRIS. A playing title shows its name, or an episode's name with its series and "S1 E3", and its TMDB artwork, keeps the position state current at every seek, pause and speed change, and answers play, pause, seeking, 10 s skips and, while `next` holds an episode, next track through `titlePlayer.playNext()`. A channel shows the programme on now, the channel and its logo, and answers only play, pause and stop, pause stopping it; once stopped Chromium has no player to offer the system, so it can't be started from there. Artwork must be http or https: Chromium refuses `file://`. Only Watch and a playing title present anything, so muted previews leave the system alone, and a view clears the session on closing only while the session is still its own, since Watch can open before the title it replaces has gone.

`player/title-player.ts` controls movies and episodes in the same element. Opening a title suspends the live stream; starting a live channel closes the title. It picks the tracks (`@mrstreamer/core/ondemand/tracks`: the remembered language, or the file's default sound and forced subtitles in its language). `audioLanguage` "original" (`ORIGINAL_SOUND`) is the language the title was made in, `originalLanguage` on a title once TMDB said, else the file's default. It seeks within what is buffered or starts a new run, ends the run after five minutes paused and resumes from there, retries a copied sound track once as converted when it doesn't start, and saves progress as above. It also holds the speed, from 0.5× to 2× with the element's `preservesPitch` keeping voices at their pitch: each run starts at it, it carries on when another episode of the series opens from the one playing, and closing the title puts the element back at 1× for live channels, which have no speed. Leaving a title while its file is still being probed closes that session too, so no provider request outlives it.

A title's Speed button (`features/watch/SpeedMenu.tsx`) sets its speed. The subtitles' timing and look (`features/watch/SubtitleSettings.tsx`) are under CC: rows of the CC menu on Live TV, sections of the title's CC panel (`features/titles/SubtitlePanel.tsx`), which also holds a download's offset and drift and online search. Every menu over the controls shares `Menu` in `TrackMenus.tsx`: it is modal, so a click outside only closes it and can't also pause, skip or change channel, and Up, Down, Home and End move between its items. While one is open, Watch and a playing title leave every key to it.

An episode carries the details of its series version (`NowPlaying.series`), so the player knows the next one: `nextUnwatched` in `@mrstreamer/core/viewing/episodes` goes by the provider's season and episode numbers, never names, finds a file the details don't show by its numbers, leads from specials only to specials, and passes over every episode that is watched, played or [marked](#episode-marks), without ever going back to an earlier one. The player reads how the series' episodes stand (`viewing.episodes`) as the episode opens, on every `viewing.changed`, as the episode ends and once more before the next one opens, so a mark made meanwhile counts. The next episode is the answer to the latest question alone (`nextQuestion`). None is offered until the record has answered. A question asked before another settles as the later one does and takes nothing from its own answer, so a countdown that runs out as an episode is marked waits for the answer after the mark. When the record doesn't answer the latest question as the episode ends or as the countdown runs out, nothing counts down and nothing opens, and the episode it last knew of stays on offer for another try. At the end of an episode with another after it, the player counts down ten seconds, unless `autoplayNext` in the preferences is off, then closes the episode and opens the next from its beginning, in the same version, as a new play. `titlePlayer.playNext` does the same at once for Play now, Next episode, N and the system's next track, and does nothing while a next episode is already starting. Seeking, closing, another title, a live channel, the removal of the subscription it plays from and the last subscription going (`resetForAccount` closes the title) drop the countdown. They also take back a next episode that was asked for and still waits for the record (`nextRequest`), as Cancel does, so a late answer opens nothing. While Settings is open, `ui-store.ts` holds the countdown (`titlePlayer.holdNext`) at the seconds it had left, so nothing starts behind Settings; a next episode still waiting for the record then is asked for again once Settings closes, and an episode that ends meanwhile starts counting then. A next episode that fails before it plays says it didn't start, with Try again and Episodes. Once an episode with none left after it is in its credits, the player asks the record, after that checkpoint, whether a numbered episode is still to watch (`finishes`), and only when none is sends `viewing.finishSeries` with every version's id and when the play began: a series whose last episode ends with an earlier one unwatched stays in Continue watching, which offers that one.

Lists keep one keyboard selection, separate from the pointer. Only the keyboard moves it or scrolls a list to it; the pointer only hovers, and the selection shows only while the keyboard was used last (`lib/input-mode.ts`). Wheel and trackpad gestures only scroll. Key handlers register once and read the current render through a ref: a handler registered again on every render can miss a key, because a state change in another keydown listener renders between listeners. Watch and a playing title listen in the capture phase and stop the keys they handle, so a tooltip can't keep Escape to itself and an Escape that leaves a layer doesn't also close the one it uncovers.

## Playback

The UI never sees provider URLs; they contain the login. `playback.open` returns a `127.0.0.1` URL with a random token, and only one session is open at a time, across every subscription: many subscriptions allow one connection, and one viewer watches one thing. Each session is a scope: closing it, by stopping, switching or quitting, aborts its upstream requests and ends their ffmpeg process. When the player requests the URL, the proxy connects upstream and then, before sending anything:

1. **Inspects** the stream (`playback/inspect.ts`): the program tables name each track's codec, each sound track's language and whether it describes the picture, and the teletext and DVB subtitle pages; the first frames settle what the tables leave open (MP2 or MP3, 8 or 10-bit HEVC, AAC channel layout). It reads at most 2 MB or 2.5 s and stops as soon as the delivery is settled. `playback.tracks` lists the sound and subtitle tracks from then on.
2. **Plans** (`playback/convert.ts`): the renderer reports which codecs its player decodes (`player/decoders.ts`, from `MediaSource.isTypeSupported`). Tracks it decodes are copied; the rest convert: sound to stereo AAC, video to H.264 with deinterlacing, 4K reduced to 1080p. `playback.open` can name a sound track by PID; mpegts.js plays the first one the program table lists, so a stream delivered as it is gets the chosen one moved to the front (`playback/program-table.ts`), and ffmpeg keeps only the chosen one. Converting keeps teletext and DVB subtitles, and every track under its own PID.
3. **Starts clean** (`playback/clean-start.ts`): for H.264 and HEVC, drops video before the first keyframe and the leading frames that display before it, so a stream joined mid-sequence starts on a decodable picture.
4. **Delivers**: straight through when nothing converts, otherwise through the bundled ffmpeg reading stdin, so the upstream URL never reaches a command line.

If the player still fails to decode the picture, the player controller retries once with `repair`, which re-encodes the picture and conceals broadcast damage.

### One stream across subscriptions

What the viewer asked last is what plays, whichever subscription it is of, and everything asked before gives way. The main runtime provides one `services/playback-coordination.ts` (`PlaybackCoordination`) for Playback, Downloads, Output and IPC. It owns the serialized opens, latest request counter, per-subscription leases and availability notifications. Playback keeps media session scopes, serving, probing and conversion; Downloads keeps its persistent queue and transfer policy. Playback reports registration and closure from its existing session lifetime, including copies with no subscription. Each ask to play or stop begins a turn (`PlaybackCoordination.begin`), a count for the whole app. An open carries its turn, and takes its place in a queue of one (`PlaybackCoordination.inTurn`): when its place comes and a later turn has begun, it fails with `superseded`, before it closes or opens anything. It looks again once the provider answered it, since a turn can pass while a file is read, a receiver's index is read or a channel's streams are listed: then what it opened closes and it fails the same way. An open still in its turn closes the session before it, of whichever subscription, and only then connects, so no provider sees a connection of this app while another has one, and the provider it leaves gets its connection back before the next is asked. The window's last word on a title's progress goes to that title's own subscription as its session closes.

Work that is slow, such as a title's file being named or a channel's streams being listed, is done before the open's place comes, and is guarded twice on arrival. The turn says whether the viewer moved on (`PlaybackCoordination.passed`). The subscription's revision says whether its login is still the one the work was done under (`Asked.revision`, `Subscriptions.stands`): an address made under a password that was replaced since isn't opened, nor one whose password was replaced while its file was read, and a channel of a subscription that went fails with `no-subscription`. A password entered again for one subscription therefore drops what was under way for that one alone, and what plays from another goes on. `Playback.closeOf` closes what plays from one subscription, for its removal, once an open under way has had its turn; `Roster.remove` calls it before the login goes and once more after, for an open that found the subscription still saved.

A download borrows a subscription's connection only between these opens, and each open takes it back before it connects (see [Downloads](#downloads)).

Nothing falls back to another subscription by itself: a channel or a version that fails says so, and the same film at another provider is the viewer's to pick. A receiver's opens go through the same turns (`Output.playChannel`, `Output.openTitle`).

Playlists list most channels as HLS (`.m3u8`), which hls.js plays instead of mpegts.js. The proxy serves it playlist by playlist (`playback/hls.ts`): each playlist the player loads comes back with its addresses, variants, renditions, segments and keys, replaced by proxy addresses with an id each (`/stream/<token>/<id>`), so the player still sees no provider address, and segments pass through as they arrive. Each request the player makes is one upstream request without retries, which hls.js makes itself, and closing the session aborts them all. A session keeps the playlists a multivariant playlist names for its whole life, and up to 10,000 segment addresses, the oldest going first: broadcasters list two hours of segments in each playlist, and rewriting one of those, every few seconds, takes about 20 ms. Nothing in the main process inspects or converts HLS: a stream's tracks are in playlists only its player reads whole. So the HLS engine reads them (`player/hls-tracks.ts`) and tells the player, which shows the same Sound and CC as for a channel the main process serves, with the same remembered languages. Sound renditions switch in hls.js, where the stream plays. Subtitle renditions (WebVTT, or IMSC) and closed captions, declared or found in the picture, come as lines from hls.js, which adds no text tracks of its own: the player puts the chosen ones on the element's subtitle track, so the viewer's timing and look apply. hls.js numbers renditions by their place in the group the playing variant uses, and again when it moves to a variant with another group, so each has an id worked out from what the playlist declares about it: a hash of its name, language and marks, with its place among any that read the same. The viewer's choice stays the same track through such a move, and when the channel opens again, as for another quality, in whatever order that stream lists them. A rendition the new stream lacks isn't found, and the remembered languages decide as on a channel opened afresh. hls.js would also turn on the subtitles a stream marks as its default; whatever it selects by itself is put back to the viewer's choice before it loads anything. It reads each line once, ahead of the picture, so the lines yet to end are kept for when subtitles are turned on again. The chosen row in CC says Loading until hls.js has read a segment of that rendition where the stream plays, which it says for every segment (`SUBTITLE_FRAG_PROCESSED`), and not until a line comes: broadcasters keep up renditions whose segments are a WebVTT header and nothing more. A rendition hls.js can't get or read stays Loading, and captions never are, since they come with the picture. DVB subtitles and teletext inside an HLS stream's segments aren't read. Chromium's own player, which plays HLS only where Media Source Extensions are missing, offers no tracks, so such a stream shows no Sound or CC.

Closed captions travel inside the pictures, in SEI messages, which mpegts.js reads but doesn't pass on. On their way out, after any conversion, `playback/caption-stream.ts` copies each picture's CEA-608 pairs into a private data stream on PID 0x1FF0, with the picture's time, in display order: pictures arrive in decoding order, and B-frames reorder them. The program table lists that stream once a picture carries captions, so a channel without them passes unchanged, and `playback.tracks` lists the caption channels found. mpegts.js passes private data on with times on the player's clock, as it does teletext and DVB subtitles.

Watch shares its Sound and CC menus with a playing title (`features/watch/TrackMenus.tsx`). For a channel the main process serves as MPEG-TS, the live player reads `playback.tracks` once the stream plays, and again each time the main process says they changed (`playback.tracksChanged`, by session): caption channels show up only as pictures carry them, which can be long after the start, and the proxy says so for the stream the player last asked for, never for one it replaced or closed. Only the answer to the newest read applies. An HLS channel's tracks come from its engine, as above. Another sound track opens the stream again with its PID. A channel opened afresh names the remembered language instead (`audioLanguage`), and the proxy picks the first sound track in it from the program table. `playback.tracks` names the track the stream plays (`playing`), so the Sound menu marks the one heard. Subtitles never reopen anything: the engine hands each private data packet to the player controller, which feeds the chosen PID to its `@mrstreamer/core/subtitles` decoder and shows the changes as a title's (`player/subtitles.ts`). The chosen languages are the same `audioLanguage` and `subtitleLanguage` preferences titles use. A channel starts with subtitles in the viewer's language only when none of its sound tracks is in it: on a channel that speaks it, they are for the hard of hearing.

Providers send a burst of buffered seconds when a stream opens. mpegts.js jumps forward when the picture falls more than 8 s behind the newest data, keeping 3 s of buffer, instead of playing faster to catch up: a 1.2× rate was audible and visible for half a minute after every start. The [playback evaluation](playback-evaluation.md) records why this design won over a bundled engine such as libmpv.

### Quality

`playback.open` takes a channel, named with its subscription by its id or any of its streams', and the main process picks which streams to try (`streamsToPlay` in `@mrstreamer/core/catalogue/variants`). A stream named in the call (`variant`), or else the one picked for the channel before (`channelVariants` in its subscription's preferences, kept under the channel's id then and found under any of its streams' ids), is tried alone. Otherwise Automatic tries the quality in `liveQuality`, Full HD when absent (`DEFAULT_LIVE_QUALITY`), then lower ones from the best down, then higher ones from the nearest up, then those not labelled, three at most; equals keep the provider's order, so a backup follows its main stream.

The proxy tries them in turn when the player asks for the stream, each request over before the next begins, so the provider sees one connection at a time. A stream moves on when the provider answers 404, 410 or another error, doesn't answer within 15 s, or ends before sending anything. A refusal (401, 403 and the like) ends the turn after its usual two retries. Its status names no cause and says nothing of what another stream would get, so the proxy stops there and asks for no other stream. A stream that failed goes after the others for two minutes, so the player's reconnects, up to four after a stream broke, don't wait for it again. A turn makes three requests at most, and nothing loops: each open tries each stream once. Against the fake provider, a 404 before the stream that plays made the first picture data arrive after 44 ms instead of 25; when no stream answers, a turn gives up after 45 s. `playback.playing` names the stream that plays and those that failed first; the line under the programme says when Automatic passed one by, until the channel changes.

Watch's Quality menu (Q) picks Automatic or a stream, saves it in `channelVariants` and opens the channel again. A picked stream that fails stays picked: Watch says why it didn't play and offers Retry, the stream Automatic would try first and Automatic itself. After a refusal it offers no other stream, as nothing shows one would be let through. Its label is the provider's word for the stream's quality; the resolution beside it is what the decoder reports, which differs when the name is wrong or the proxy reduced 4K to 1080p. Settings > General > Live TV sets `liveQuality` and clears every subscription's picks. Removing a subscription forgets its own, as their ids are the provider's.

### When a channel fails

`playback.failure` says why the provider didn't deliver a session's stream, as a `StreamFailure`: its kind, the HTTP status where it answered one, and for the rest a sentence that can quote ffmpeg or an address. The live player keeps the kind and the status and drops the sentence (`classify` in `player/player.ts`), so the `PlaybackProblem` of a stream that failed carries no free text. An engine's own error counts by its kind alone. A session that didn't open and a receiver's trouble aren't classified: those members keep their `AppError` or `OutputFailure` as it came, detail included. For a session that didn't open, `describeOpening` in `problems.ts` says a fixed sentence wherever the error could quote a server's name or an engine's words. A receiver's trouble keeps the words `receiverProblem` in `Output.tsx` had for it, which quote a detail only for a Cast receiver that isn't available. A status proves little: 401, 403, 429, 458 and 509 all count as a refusal, and none of them says whether another device holds the connection, the login stopped working or the channel isn't offered in the viewer's country. So the words name the refusal and its status, and put a check as a condition.

A stream that breaks, or doesn't start, is tried again after 1, 2, 4 and 8 seconds when the network or the provider failed. Those four reconnects are the channel's (`recovery` in `player.ts`), on this computer and on a receiver alike, and a break gets all of them again only after the stream played for 30 seconds (`STABLE_PLAYBACK_MS`). Played means the picture's clock moved: the engine counts it in its once-a-second check (`Engine.played`), without time paused or waiting for data and without the jumps that catch up with live. For a receiver it is the time between its words that the channel plays, not what it held paused or buffering. A stream that comes back for a few seconds and breaks off again therefore ends as failed after four reconnects. The viewer choosing the channel again, Retry, another quality or another channel starts afresh (`begin`). Every start is a new selection, so a wait that ends after Stop, a channel change or a change of output opens nothing, and a wait that ends after the viewer left Watch leaves the channel failed: what would open is a preview, which never reconnects. A refusal, a missing stream and an unplayable one aren't tried again by themselves, and a picture the player can't decode still gets its one repaired try first.

A failed phase carries the problem, when it failed, and what the channel went through: whether it ever played, the reconnects made, and how often it came back and broke off again. `features/watch/problems.ts` turns that into words for every place that shows them. `PlaybackState.tsx` puts a title, a sentence, a small line of what was observed and the actions in the middle of Watch. A channel that never played says the provider didn't answer when the main process saw that, and that no picture arrived when only the player noticed, since data without a picture looks the same to it. One that played says it lost the stream, and one that kept coming back says it keeps dropping. The actions follow one order: Retry where trying again can change the answer, then Quality while the channel has a stream the last try didn't reach, or Next channel when it has none, then Channels. Quality opens the menu and starts nothing. A refusal offers no other quality. A rejected login offers Update login, and a password or link the keychain lost offers to enter it: both open Settings > Subscriptions on that subscription's form (`openSubscription` in `app/ui-store.ts`). With several subscriptions saved, the sentence names the one whose channel failed. The mini player and `ReceiverBar.tsx` say the title, the bar with the provider's status. A receiver's own trouble, such as a lost connection, keeps its words and Try again.

Before a failed session closes, the player asks `playback.playing` once more and keeps the answer, so the quality menu's rows say what that try got from each stream: the status the provider answered, the one that arrived and didn't play, and those it never reached. Only that try counts, and the proxy's two-minute memory of failed streams stays in the main process.

An engine says when its clock has stood still for three seconds though it should move (`Engine.onWaiting`), well before the fifteen that count as a broken stream. Watch then shows "Waiting for data" where a pressed key's word shows, as a standing note with nothing that moves. Previews hear it too and show nothing. `PlaybackAnnouncement` is a live region that stays in Watch and holds the title and sentence of a reconnect or a failure, so a screen reader says them once. Which attempt a reconnect is at, and the seconds to it, are outside it. R retries a failed channel where Retry shows, and Enter presses what Tab reached among a failed channel's actions, while everywhere else Enter still opens the list.

### Movies and episodes

Providers keep movies and episodes as files behind a redirect. Most answer byte ranges; others send the whole file from zero even when asked for a range: two thirds MKV (H.264, sometimes HEVC, with E-AC-3 sound in several languages and dozens of SubRip subtitles), a third MP4, and a few AVI, MPEG-TS and MPEG-PS. Chromium's own player can't pick among their sound tracks or show their subtitles, and doesn't decode E-AC-3 on Linux, so every title goes through ffmpeg (`playback/title.ts`, `services/playback.ts`):

1. **Probe.** `playback.openTitle` closes any open stream, opens a title session and runs the bundled ffprobe on the proxy's `/source/<token>`, which forwards ranges to the provider one upstream request at a time; a new one, such as a seek, ends the one before, and a refusal is retried after 0.15, 0.4, 1 and 2 s, since panels take a moment to free the connection just closed. ffprobe decodes the first keyframe too, since only a decoded picture shows the closed captions inside it. The session answers with the tracks, labelled in their own language (`@mrstreamer/core/ondemand/tracks`), and the length. Each subtitle track has a format: text (SubRip, ASS, MP4 text, WebVTT), picture (PGS, DVD, DVB, XSUB), teletext, one track per subtitle page, or captions (CEA-608 tracks, and captions inside the picture). Formats outside these aren't listed.
2. **Run.** Each request to `/title/<token>.mp4?start=&audio=&subtitle=` runs ffmpeg from that position with those tracks and replaces the run before. Video the player decodes is copied, the rest becomes H.264; sound likewise becomes stereo AAC. Copied video starts at the keyframe before the position, so ffmpeg keeps the file's timestamps (`-copyts`) and PUTs a one-packet `framecrc` report of the first video packet back to the proxy, which reads the keyframe's time from its first line and answers with `x-start`. A run of a file's last seconds can be over before the proxy has read what it sent, so the proxy waits up to two seconds for the reports of a run that ended well. The fragmented MP4 goes to the player. The chosen subtitle track goes beside it, PUT to the proxy packet by packet as ffmpeg reads it: text subtitles as WebVTT, the others as packets the player decodes. PGS goes as it is stored (the `sup` muxer), since ffmpeg only learns how long a PGS picture shows when the next arrives; DVD and DivX pictures as DVB subtitles, which carry their length; DVB and teletext as they are; a picture's captions as its SEI units alone (`filter_units`); and a CEA-608 track as its own packets, not through ffmpeg's caption decoder, which starts each run without the hidden memory, mode and cursor the captions before it set up. Copied AAC passes `aac_adtstoasc`, which MPEG-TS files need. `delay_moov` lets ffmpeg describe copied AC-3 and E-AC-3, and a start at zero doesn't seek, which skips seconds of some AVI and FLV files. `-thread_queue_size 64` is for ffmpeg 6, which otherwise switches between its reading and its writing thread for every packet of its one input; ffmpeg 7 and later queue packets by themselves.
3. **Play.** `player/title-engine.ts` feeds the fragments to Media Source Extensions with the timestamp offset that puts the first fragment at `x-start`, so the element's clock is the title's: the position is `currentTime`, a skip into what is buffered only moves `currentTime`, and subtitle times need no arithmetic. With subtitles on, the run reads their feed beside the picture, described below; the picture never waits for it. `player/mp4.ts` reads the codec string MSE needs from the first boxes. Reading stops once 60 s are buffered ahead and starts again below 40 s; while paused nothing more is read and the provider's connection idles until playback moves on. When the provider breaks off a file, ffmpeg can still end its run as if the file had ended; the proxy saw the break, so it ends the run's response as broken, and the player reconnects instead of playing out to a false end.

### Subtitles the app draws

`@mrstreamer/core/subtitles` decodes DVB subtitles, PGS, teletext subtitle pages and CEA-608 captions into changes of a screen: lines of text, or pictures on a canvas the size the subtitles were made for. Teletext shows only a subtitle page's boxed text, with the page's national character set and the accented letters enhancement packets add; captions build up as pop-on, roll-up or paint-on. `player/subtitles.ts` shows each change from its time on, on a layer of its own that `Picture` moves with the video element. Chromium would draw text cues itself, inside the element and so under the controls and their gradient, which dims them. So both of the element's tracks are hidden: Chromium times their cues on the element's own clock and draws none. Text goes on the subtitle track as cues, a title's WebVTT lines and the lines decoded from teletext and captions alike, and the layer shows those due where the clock is. Each is drawn as its cue's own parser reads it (`getCueAsHTML`), so line breaks, italics, bold and underline hold, and a file can't slip markup in. The classes WebVTT lets a tag carry are taken off first: on the layer they would be the app's own, so `<c.hidden>` would hide its text, and Chromium gave them no style when it drew cues itself. Pictures go on a canvas in the layer, stretched over the area the picture fills, as broadcasts mean them, and cues on the metadata track show and hide them. Nothing is drawn between changes. The text is read again when Chromium says a cue started or ended, after a seek, and whenever `subtitles.ts` adds, moves or removes a cue itself, because Chromium says nothing of a cue that is removed or moved off the position. The canvas is drawn at a change or a resize. Cues more than 30 s behind go.

The text sits where Chromium drew it, measured in the app: the system's sans-serif at 5% of the element's smaller side, whatever the picture's shape, centred, each cue 4 px above the foot or the cue under it. Cues due together stack upwards, and each stays where it first showed: one that ends under another leaves its place empty for the next. Two things differ from Chromium, which stepped a cue up by a line's height until it fitted. A cue of several lines sits 4 px lower for each line after the first, and the small size rests at the foot like the others, where Chromium left it most of a line higher in a full window.

Subtitles show only inside Watch and a playing title, not in the muted previews. There `styles.css` puts the layer above the controls, so text and pictures are as bright while those show, and under the channel list, the end of an episode, the window bar and the menus. While the controls show, the views set `data-controls`, and `styles.css` moves the layer up above them.

The viewer's timing and look live in `subtitles.ts`, not on a run, so they hold through seeks, track changes and new runs. Timing applies to text: every text cue keeps the times its file gave it and shows `delay` seconds later or earlier, set again on the cues already there when it changes, and back to zero for each title and channel. Pictures keep their own times. The look, kept as `subtitleLook` in the preferences, is a size, a box or a shadow behind text, and a low or higher place: `styles.css` sizes and shades the text from it, `paint` draws pictures bigger or smaller from the middle of the picture's foot, and both rise by the same share of the picture.

Each change ends the one before it, even one that named a later end, as a DVB page does with its time-out; one that names no end stays until the next. Chromium sends no exit for a cue whose end arrives after the position has passed it, so `subtitles.ts` takes that picture off itself and reads the text again. A stream that stops or opens again takes its cues with it, in the live player's `release` and a title engine's `destroy`: their times are on a clock that no longer runs.

### Subtitles at a position

A file holds a subtitle only where it begins, and a run reads on from the keyframe before its position. What is on screen there began before it, and may build on things sent long before: a PGS display set can show an object with a palette sent earlier in its epoch, a DVB page update shows the regions of the last acquisition point, a teletext page keeps the rows sent since it was last erased, and a caption channel holds a second screen in memory that a later command swaps in. A run by itself shows such a subtitle only from its next change, or wrongly.

The picture never waits for that. The player asks for a track's feed and for the run together: `/title/<token>.mp4?only=subtitles&start=&subtitle=&page=` answers JSON lines with times in title seconds (`@mrstreamer/core/subtitles/feed`), and `x-codec` names the decoder for packets.

1. **What came before.** The track's entries from the last fresh start that has taken effect by the position: a PGS epoch start, a DVB acquisition point or mode change, the erased header of the chosen teletext page (`freshStart` in `subtitles/decoder.ts`). A decoder that begins there shows what one that read the whole stream shows. Text depends on nothing, but a line can last any length of time, so the feed has to know every line before the position to say which are on screen. The player holds packet changes back through its decoder until the next line says what they are worth. Independent text lines go on the track as they arrive, including upcoming lines from the run while recovery continues for lines that began earlier.
2. **`ready`.** Everything before the position has been sent. The player shows what the last change left on screen where the picture has got to by now, and each change after it, and draws the picture due there without waiting for Chromium's cue events (`drawNow`); lines of text already show as they go on the track. Until recovery settles the title's view says "Subtitles loading" where a changed speed shows (`features/watch/Flash.tsx`), a speed or timing change shows over it for its moment, and the chosen track's row in the menu says Loading.
3. **`unavailable`.** What came before can't be had: reading it would take more of the provider than a reading may (`limit`), the provider put another file behind the address (`changed`), the file isn't one the track's past is read from (`unreadable`), or the provider didn't answer (`network`). The picture plays on and the track stays chosen; the view says "Subtitles unavailable" for five seconds and the menu row says Unavailable. Incomplete packet state is cleared. Text already read stays unless the file changed, which clears every kind. The track's status recovers from the first thing the run reads that stands on its own, which the feed marks with `ready` and its time: a packet that starts the track afresh, or the next line of text, or the next packet of a track whose packets never start afresh, as captions, which is what a run alone ever showed of those.
4. **What the run reads.** The run's own subtitle output goes on to the feed, from a little after the position on. A packet may sit a little off the picture of its own time, so that stretch still comes with what came before: 1 s in Matroska and MP4 files, which keep to hundredths of a second, and 2.5 s in the others, as transport streams send pictures ahead of their time by as much as their encoder's buffer. A DVD picture's end, which ffmpeg writes with the picture, stays with it. Packet output the run read while the feed wasn't ready follows what came before, 2 MB of it at most; a run that read more leaves the feed `unavailable`. Text joins the run at once and is not sent a second time when recovery settles. Each feed remembers the exact live text it sent, within the same 2 MB bound, across replaced runs; a new position gets a new feed and replacing the file clears that memory. Recovery still scans the past within the same budgets, so long-lived earlier lines can arrive later without holding upcoming text back. The player's 35-second loading deadline leaves independent text and its feed running and marks only the history unavailable; packet tracks still stop and clear at that deadline.

The proxy keeps what it reads of the chosen track while the session lasts (`playback/subtitle-history.ts`): each packet or line with its time, and the stretches of the file's clock read through whole, 4 MB at most. A run's own reading counts, so a position played through costs nothing more. The rest it reads from the file itself, for Matroska files (`playback/matroska.ts`): the file's descriptions and index, then from one block's header to the next from the block the index lists last before the stretch, taking the track's packets whole and passing over the picture and sound, until the picture is a second past the stretch. The index says where to look, never that a stretch holds nothing: nothing obliges a file to list every subtitle packet, and a missing entry would hide the end of a picture. The packets taken go to ffmpeg in a small Matroska file of their own on its input and come back the way a run's do, whatever the track's coding. It reads back from the position: to the nearest packet the index lists for the track, then the one before, then twice as many each time, until a fresh start is in what it keeps; text from the start of the file. An MP4's text tracks need none of this, as ffmpeg starts each MP4 track at its own sample before the position. A track in any other file, and captions inside the picture, are `unavailable` at a position that isn't the start.

Every request for the file takes a turn at the provider, one at a time, playback first (`playback/upstream.ts`). ffprobe's and ffmpeg's open-ended range requests get bytes from the position they asked for. If a provider answers a nonzero range with HTTP 200 and a known whole-file size, the proxy reads that one answer forward, drops the prefix and serves HTTP 206 with the remaining length and Content-Range. A position at or past the size gets 416. For a nonzero request, a 200 without a known size or an answer naming a different start that is not the whole file from zero ends the request without sending misplaced bytes. A 206 whose headers do not establish its range passes through as before. Requests from zero keep their single pass-through. A run that is starting has the provider to itself until its picture has reached the player, and a new request of ffmpeg's, as it makes to start and to skip, ends a reading's request at once. After that a reading gets a turn when ffmpeg has left what it was sent for 0.3 s, as it does once the player has 60 s buffered or is paused; or between two of ffmpeg's requests from when the player has 10 s buffered until it has fewer than 5, which the player says twice a second while its subtitles load (`only=progress`). While a reading takes turns, the proxy asks the provider for ffmpeg's file about a second's worth at a time; ffmpeg's answer stays the one it was promised, the same length from the same position, and each part has to be the bytes that follow of a file of the same size, or the answer ends there and ffmpeg asks again. A reading asks for about a twentieth of a second's worth at a time, 16 to 256 KB, or the least when the stretch is more than it may take. Readings hold the provider for a tenth of any ten seconds at most while a run plays, and for a quarter of a second when ffmpeg waits. One position's reading may take 8 MB, 256 requests and 30 s; past that the feed says `limit`. A provider that knows no byte ranges keeps its one answer without yielding turns or resuming it. Recovery asks it for nothing: a feed or a receiver segment gets the lines from before its position only from what a run from the start kept of the same file, under the same identity rules as any provider, and is `unreadable` otherwise. Keyframe-index reads refuse it. A seek or resume must download from zero to the position. Local copied-picture startup waits 30 seconds from the later of its start and the last prefix byte dropped by `serveSource`. Advancing through a whole-file answer keeps that wait alive; once dropping ends, the picture has a full 30 seconds, and a stalled drop fails after 30 seconds without progress. Abort settles the wait immediately. The same source sends `playback.readingAhead` with the session id at most once every 3 seconds, only when dropped bytes advance. The title player passes matching notices to its starting engine. Its existing watchdog measures from the later of when the run was asked for and its last notice: 45 seconds without any picture, and 30 seconds to start moving when the element is not paused or seeking. With no notices those rules are unchanged, and ranged providers send none. There is no absolute read-forward cap; the viewer can leave at any time. Receiver segments keep their 30-second deadline, so a large or slow far segment can still return 504. A receiver timeout ends its read-forward; asking for the segment again can start another read from zero. A request cut short has left before the next is made, and a refusal is still retried, since a connection kept from an earlier request would otherwise carry the next one to the provider first.

What is kept is of one file (`playback/source-identity.ts`). Each answer's size and mark are compared with what the same address said before, after redirects, since a provider's servers each give their own ETag for the same file: another size, or another mark from the same server, is another file. Then everything kept goes, with what ffprobe read for the next time the title opens, and a feed that gave the player the old file's subtitles says `changed`; the next feed reads the new file, once ffprobe agrees the track is still of the same kind. Playback is never stopped for it: ffmpeg gets what the provider sends, as it always did, so a file whose ETag is another with every answer plays, without subtitles from before a position. A weak ETag, or a Last-Modified less than a second older than its answer, vouches for nothing: a file known by its size alone is read anew for every position, and so is one that a server answers for the first time since it was read. An answer that doesn't say what it holds, as a whole file without its length, vouches for nothing either, and one from a server that still has a replaced file is of that file: what a run reads from either is never used again, and what is kept starts anew with the next answer of the file in its place.

Measured with Electron 44 against the fake provider: a run starts in about 1.1 s and a seek outside the buffer in 0.9 s; starting 10 minutes into a file read 57 MB, probe and a minute ahead included, and nothing more while paused. [Playback evaluation](playback-evaluation.md#movies-and-episodes) records how this design was chosen.

Against a synthetic provider with one connection that takes 20 ms a request and sends a 7.5 Mbit/s file at ten times that speed, the first picture after a skip came as soon with the feed asked as without it, 0.8 s. A PGS picture that began two seconds before the position took 28 requests and 6.4 MB: 1.3 s with the provider to itself, and 8 s after the picture beside a run still filling its buffer. At twice the bitrate the same reading ran out of its 30 s, and at one and a quarter it never got a turn; the picture played the same either way. A picture that began 16 s before the position is more than a reading may take there, 18 MB.

## Downloads

A download is a movie or one episode, by its exact provider file, kept on this computer to play without a network or a subscription (`services/downloads.ts`). Each is a record in the `downloads` table of `mrstreamer.db`, a JSON document per row that builds before 0.0.10 never read, and a folder of its own in `<data>/downloads/<id>/`: `media.<ext>`, `media.<ext>.part` while it transfers, and the `poster` and `wide` pictures kept for it. The container names the extension only when it is a short run of letters and digits; anything else is `bin`. Paths, addresses and logins stay in the main process: the window sees `Download` rows (`@mrstreamer/contracts/downloads`), with artwork at `mrstreamer://download/<id>/<poster|wide>`, a scheme `index.ts` answers from the record's folder alone. Queuing (`downloads.add`) reads the title's details and an episode's season as the details sheet did, resolves its file with `OnDemand.file`, and fetches the two pictures once, so a copy shows and plays with nothing asked of anyone.

One download transfers at a time, of whichever subscription: the first in the queue whose subscription plays nothing. It borrows that subscription's provider connection from `PlaybackCoordination.lend`, granted under the same open lock as every open, and only while no session of that subscription is open. Every open of a provider's stream, here or on a receiver, takes it back first in its own turn (`PlaybackCoordination.reclaim`): the lease's signal aborts the transfer, and the open waits for its `release`, which comes only once the transfer's reader was cancelled and its partial file closed. An open whose release hasn't come within ten seconds fails as a network failure without asking the provider anything, and the lease stays until the download gives it back: playing again then waits for it once more. The download then waits in the queue with its partial file; `PlaybackCoordination.busyChanged` says when the subscription is free again. A download of another subscription isn't touched, and a copy's playback takes no provider connection.

`downloads/transfer.ts` streams the provider's answer into the partial file with backpressure, so at most what the disk hasn't taken yet is in memory. It goes on from the bytes there only when the provider proves they are of the same file: a 206 starting where they end, of the same total size, with the same strong mark (`strongMark` in `playback/source-identity.ts`) from the same address after redirects, query included: two queries of one path can be two files under one ETag, so a changed query, as a signed one, starts again. `If-Range` asks for that. A 200 is the whole file again and is written from the first byte; a range of another file is asked for again from the start; a file without a strong mark can't be gone on from. Each such start says so (`restarted`). The address is kept on disk only as a fingerprint of its origin, path and query (`resourceKey`), since an Xtream file's path holds the login. What the partial is of is written down in step with its bytes (`identify`): the old file's mark stays while a fresh start may still not go ahead, as when the disk has no room for it; once it does, the partial is written down as of no file before it is touched, and as of the new one once a byte of it is on disk. The app stopping or a write failing at any moment leaves the partial under a mark it holds, or under none, which starts it again. A refusal is asked again after 0.5, 1.5 and 3 s, as the provider frees the connection of the request before. A disk with less room than the rest of the file fails before writing; a write that fails says whether the disk is full or the folder can't be written. A transfer that ends with every byte the provider named is flushed, renamed into place, and only then marked complete; a rename that happened just before the app stopped is found on the next start.

A copy plays through the same title session as a provider's file, of another origin (`TitleOrigin` in `services/playback.ts`): `Playback.openCopy` gives the session `fileRequest` (`playback/file-source.ts`) in place of the provider's request, which answers ranges, 416 and a strong ETag from the one path that session was opened with. ffprobe, the runs, seeking, the tracks and subtitle history read through the loopback proxy as before, and no subscription, catalogue or verified-file record is asked. Opening a copy closes what plays here and leaves a receiver's session alone; a copy never moves to a receiver. Saved subtitles of the exact provider file come with a copy at completion (`SavedSubtitles.duplicate`), each result only when the playback that saved or timed it proved the same bytes: with every result it saves or times, `OnlineSubtitles` records in the same transaction the file's size and marks as its session read them, by `resourceKey` (the `saved_subtitle_proofs` table), or no proof when the session couldn't prove them: an answer without a mark, of a replaced file, or from another path or query than the one read first (hosts may differ) leaves the session's file unproven until another file is behind its address, and the download's own answers must match that result's proof. From then on they are the copy's (`subtitlesOfCopy`) and outlast that account's login, expiry and erasure. Online search is refused for a copy without asking anyone. In the window, `NowPlaying` is a `ProviderNow` or a `CopyNow`: a copy saves its progress with the copy (`downloads.recordProgress`), and has no next episode, receiver or viewing record.

Removing a subscription cancels its unfinished downloads, before its login goes and once more after (`Downloads.subscriptionGone`); its copies stay, named "Subscription removed, copy kept" until an account of the same key is saved again. Deleting a download removes its record first, so nothing writes it back, then stops its transfer, closes its playback, forgets its saved subtitles and removes its folder; a folder no row names is removed on the next start. Only a table read whole decides that: a row this build can't read, as a later build's, keeps its folder, and when the database can't be read nothing is removed and listing or queuing fails with why. Quitting stops the transfer and keeps the queue.

## Receivers

Playback goes to this computer or to one receiver on the local network: a Google Cast device on Windows, an AirPlay receiver on macOS. Linux builds offer neither; `MR_STREAMER_CAST=on` turns Cast on there for trying it. Nothing has been tried on a real receiver yet: the suites and the [end-to-end run](testing.md#receivers) play on stand-ins, and the first hardware test is the owner's, on a nightly.

`services/output.ts` owns it. It holds the adapters (`receivers/adapter.ts` is their port), the receiver connected, and what it plays. Each thing sent to a receiver gets a generation number. A command names the generation it is for, and a command or a receiver's word about an earlier one is dropped, so a late status never moves the wrong title. What the receiver confirms is the state: `output.changed` carries it to the window, and the window's controllers show it rather than what they asked for. A title counts as ended only when the receiver says it played to the end, never when it was stopped, replaced or lost.

The service opens the session itself through `Playback`, so there is still one session and one provider connection: opening for a receiver closes what played here, and the other way round. It saves a title's progress from the position the receiver confirmed, once a minute and on pause, end and stop, for the subscription the title names. The viewing record refuses it once that subscription went, so it never lands under another, and removing the subscription a receiver plays from ends that playback first (`Output.subscriptionGone`), while one that plays from another subscription plays on. A receiver that takes a load and asks this computer for nothing within 10 s fails as `not-fetched`, which is how a firewall shows; the next try is served on this computer's next address, where it has several. Going back to this computer closes the receiver's session before anything opens here.

### What a receiver is served

A receiver can't reach `127.0.0.1`, and must never see a provider address. A receiver session gets a listener of its own on the address of this computer that reaches the receiver: the one the Cast connection uses, or the best ranked private address for AirPlay, where the system doesn't say (`playback/lan.ts` leaves out tunnels and carrier-grade NAT). It serves only `/r/<token>/…`, to clients on private addresses, with a fresh token for every load, and it closes with the session. The proxy's own routes, `/stream`, `/source`, `/title`, `/report` and `/hls`, stay on loopback. The private-address check narrows who can ask; the token is what keeps the stream to its receiver.

A movie or episode is served as HLS with a playlist of the whole title, so the receiver knows its length and can skip anywhere (`playback/receiver.ts`). Segments are made when asked for: ffmpeg's `segment` muxer runs from the segment the receiver wants and POSTs each one back to the proxy on loopback.

- **Copied video** is cut at keyframes the file's index names: Matroska Cues (`playback/matroska.ts`) or an MP4's sample tables (`playback/mp4-index.ts`), read with a few range requests. Segments are about 4 s and as uneven as the keyframes.
- **Every segment is checked** before a receiver gets it: its first picture must have the time the playlist promised and its last must fall before the next segment's. An index that lies, or one too sparse to cut by, makes the session convert from there on.
- **Converted video** gets keyframes forced at the same starts, so the playlist never changes.
- **The clock** is the title's: the first picture of the file sits at 10 s in every segment's timestamps, whichever run made it.
- **Sound** the receiver decodes is copied and the rest becomes stereo AAC. Both adapters name H.264 and AAC only until a receiver has shown more.
- **Text subtitles** go beside the picture as a WebVTT rendition, one track per load, cut at the same starts. A line that began before a skip is read from the file's index as for this computer. Picture subtitles, teletext and captions aren't sent: the picture is never re-encoded to burn them in, and the menus mark them "Here only".
- **ffmpeg never runs ahead.** It doesn't wait for a POST's answer, so each segment's address carries a user name, which makes ffmpeg send `Expect: 100-continue`, and the proxy answers only when its store has room: at most three segments ahead of the receiver and one behind, and no new one while it holds 160 MiB (`playback/segment-store.ts`). A segment is 96 MiB at most, so the store stays under 256 MiB. A receiver that stays away lets the run end and the provider's connection go; asking again starts one. A segment not made within 30 s answers 504.
- **A file the provider replaces** mid-session ends the load, as its index no longer describes it. Any answer of another file than ffprobe read counts, by its size or, at the same size, by its server's mark.

A channel is cut into 2 s segments by the same muxer from the one upstream stream, kept in memory, the newest four in its playlist. A channel that is HLS already keeps its playlists, with their addresses pointed at this computer as for the local player.

### Google Cast

`receivers/cast` is a sender of its own, with what playing one HLS stream needs: `discovery.ts` asks for `_googlecast._tcp` over mDNS while the list is open, `channel.ts` frames the Cast channel's messages by hand, and `session.ts` starts Google's Default Media Receiver, loads the address and follows its status. Frames, names and waits are bounded, unknown fields are skipped, and a message sent in parts is put together up to a limit. The suite reads and writes the same bytes with protobufjs and Chromium's `cast_channel.proto`, so the hand-written framing can't drift from the schema.

The Cast channel is TLS, and the app accepts the device's certificate without checking it and skips Cast's device authentication. A device on the network could therefore pose as a Cast device and receive a stream address. It gets no login and no provider address, and the address works only while that stream plays. Verifying devices needs Google's certificate chain and revocation lists, which is why the alternative is a maintained Cast library rather than more code here.

A connect given up while the device still starts the app stops that app once the device names it, and the next connect waits for that, so the stop can't reach the app the next one starts.

### AirPlay

Electron can't AirPlay a stream, so the app comes with a helper: one Swift executable (`native/airplay`, built by `scripts/build-airplay-helper.sh`) around `AVPlayer`, `AVRoutePickerView` and `AVRouteDetector`, for macOS 12 and later. `receivers/airplay` starts it on first use and speaks JSON lines with it over stdin and stdout; a helper that names another protocol version is refused. The system's own list picks the receiver, opened at Live TV's More button or the title's output button, and the app never learns the receiver's name. macOS names no route a player uses. The one documented sign that the viewer chose a receiver is `isExternalPlaybackActive`, which shows only for a player that holds video, so while the viewer chooses the helper's player holds two seconds of black picture of its own, paused and without sound. A connect counts only once that sign is on, and it stays the authority after: off for good means the receiver let go. A helper that dies is started again three times at most, and quitting kills what doesn't exit.

The list is AVKit's, and only AVKit says when it is up, so the picker (`Picker.swift`) keeps the app's request apart from the list. A request ends with one `closed`. The list comes a moment after the press that opens it, and goes a moment after the press that closes it, or by itself when the helper stops being the active app. The helper's window stays in place until the list said it went, or a wait of half a second for its word ran out. Taken out of sight first, a list stays up unseen whenever the helper isn't the active app, and the next press closes it instead of opening one. A list that comes up with nobody waiting, or while its window is on no display, is pressed closed. A press in another app ends the request, and so does another app with a Dock icon coming to the front. The system's own agents have none, so one of them coming to the front ends no request. The list may still go by itself then, and whether it stays up while a TV's code is typed is untried. A press the helper hears with the pointer over one of its windows that shows, other than the one it puts at the button, counts as a press at the list and ends no request. The list was such a window on the one Mac where the helper's windows were read, with rows another process drew, and whether macOS tells the helper of a press on them is untried. When a press brings no word in time, the picker's real button shows for the viewer to press, and one request gets six presses at most. With `MR_STREAMER_AIRPLAY_LOG=1` the helper says where its window was, on which display, and whether it was the active app, each time a list is asked for and each time one opens.

### In the window

`player/output.ts` keeps the status for the views. The two player controllers follow it: with a receiver connected, what they are asked to play goes there through `output.playChannel` or `output.openTitle` and `output.playTitle`, and their state is the receiver's. A channel or title playing here when a receiver connects moves to it at its position with its tracks, and Play here lets the receiver go first, then plays here from where it was. Opening the list again changes nothing by itself: the receiver plays on while the list is open, and stays when the list closes with nothing picked or with the same receiver. Another receiver takes its place only once it answered, and a title is then opened and loaded afresh there at the position last confirmed, as it is when a lost connection comes back. A receiver that lets go by itself leaves a title held, or closes it when its view isn't on screen, and leaves a channel stopped.

Live TV puts Sound, Quality, Playback and Play on in More (`features/watch/LiveMore.tsx`); titles retain the output button between volume and mini player (`features/watch/Output.tsx`). Where the app lists receivers itself it opens a menu like Sound's, which closes once the receiver answers; where only the system does, it opens the system's list. The system's list opens from a place on screen: the visible More button on Live TV or the output button on a title, measured when the list is asked for, or the middle of the window where no view shows one. O in the mini player, which has no such button, puts the window back first, full screen again where it was, and opens the list once it is. It opens nothing when the viewer asked for the mini player again meanwhile, closed the view or removed the last subscription. The O belongs to the view that took it, so Watch or a title open again in its place by then gets no list either. A list that was asked for stays its view's. Watch and a playing title say while they are on screen (`outputs.viewShown`), and the page sends each list under a name of its own. When the view closes, or the last subscription goes, the page takes back the lists still asked for from there with `output.closePicker`, each by its name. The output service takes down the list of that name alone, open or still waiting for the window, so a view that closes late takes nothing from the list asked for after its own, and what plays stays as it is. A list asked for on a page, as Try again in the bar at its foot does, has no such view and is the window's alone. `output.pick` carries the place in the page's CSS pixels, and the main process turns it into screen points with the page's zoom and the window's own place (`index.ts`). Once the window moves, changes size, is minimised or goes out of sight, the main process takes the list down with `Output.closePicker`. That ends the wait at the list and nothing else, so a receiver that plays goes on. A window out of sight opens no list. A list asked for while the window is on its way into full screen, or within a quarter of a second of its arrival, waits until then: as macOS finishes the change of Space it gives the window's app the front once more, which takes it from a helper that opened its list before, and the list then closes by itself. On one Mac that happened to lists opened up to 63 ms after `enter-full-screen`, and the system names no event for it. The main process hands that wait to the output service with the request (`Output.pick`), so the list is the service's from when it is asked for. Play here, a receiver picked in the app's list, a newer list, the view it was asked from closing, the window moving or closing, and the app quitting each end a list that still waits, and none opens once the window has settled. The place counts for the window that was asked only: one that closed opens no list, nor does another in its place at the same spot. A window that had the keyboard when the list was asked for (`BrowserWindow.isFocused`) and has lost it by the time it settled opens none either. The viewer went to another app, where the list would open over that app and its helper would take the keyboard. The main process compares those two moments and ends no list on `blur`. macOS takes the keyboard from the window for a moment as it leaves the mini player, 11 to 38 ms in three traces on one Mac, and an O can arrive in that. And once the helper is asked for the list, it follows where the viewer goes itself, and takes the keyboard from the window to do so. The way out of full screen takes no list down. A connect that reaches no receiver says why for a few seconds while what played here plays on, and one the viewer gives up says nothing. It shows on macOS whether or not a receiver is in reach, since the system's list is also where a missing one is diagnosed. `features/watch/ReceiverBar.tsx` stands at the foot of every page while a receiver is connected, and pages and the details sheet end above it (`--receiver-bar`). No page previews meanwhile, since the provider's one connection is the receiver's: the main process refuses a preview's open while a receiver is the output, and `Playback.open` refuses it again in the open's own turn while a receiver's session is open, so a preview asked for just before a receiver began closes nothing.

A channel follows the receiver's word too: one it holds paused or buffering, as after Pause on the TV's remote, reads so in Watch, in the bar and in the system's controls, and the system's Play has the receiver play on with the stream it holds (`output.command`) instead of opening the channel again.

`player/media-session.ts` plays a silent loop in step with the receiver, because Chromium offers the system only a window that makes sound: the media keys and the system's controls then work the receiver. The app holds a power save blocker while a receiver plays, so the computer doesn't sleep under it. A page that starts while a receiver plays, as after a reload, asks `output.status` and `output.playingTitle` and takes up what plays (`app/receiver-playback.ts`). The lists say what it is, so it takes up only what the receiver still plays once they answered, the same receiver, session and load, as the status says it by then, and nothing once the pages made way for Connect, as when the last subscription was removed, or the viewer played something else.

### The window's lifetime

On macOS the app outlives its window, and a receiver's playback needs the window's page, which counts down to the next episode and holds the system's media session. So while a receiver is the output, connected or gone with what it played still to pick up (`output.remote`), closing the window only puts it out of sight (`index.ts`):

- **The page runs on as if on screen.** Chromium wakes a hidden page's timers once a minute after the first, which would hold the next episode back by minutes, so background throttling is off for the window while it is out of sight, and on again once it shows. A full-screen window leaves full screen first, since macOS shows a black screen in place of one that hides.
- **The Dock brings the same window back.** `activate` shows it; there is never a second one.
- **The window closes for good once the receiver lets go**, before its page hears of it. Nothing plays here unseen, and no preview takes the provider's connection for a window nobody sees.
- **With no window, nothing plays and nothing connects.** A window closed while playback is here ends its streams, as before, and gives up a connect still under way.
- **Quitting closes the window whatever plays.** `before-quit` says so before the windows are asked to close. An update's restart closes the windows before `before-quit`, so Electron's `before-quit-for-update` says so too; without it the restart would wait forever for a window that only went out of sight. The quit then ends the receiver's playback within each adapter's own bound.

Windows and Linux quit with their window, which ends the receiver's playback.

## Updates

The app never downloads or installs on its own; see the [user guide](../user/updates.md) for the behaviour.

- **Discovery** (`@mrstreamer/core/updates/feed`): one request reads the feed the release workflow publishes to GitHub Pages, `updates.json`, naming the newest complete release of each channel (see [releasing](../maintainers/releasing.md#update-feed)). Only when the feed is missing or broken does it ask GitHub's API instead, two unauthenticated requests that share GitHub's limit of 60 an hour per network address: not when offline, and not while GitHub said it limits requests from this network (a 403 or 429 with no requests remaining, or a Retry-After), until the time it named. A failed check says why (offline, busy until a time, an HTTP status, or an unreadable answer), and the diagnostics log records each source's status and rate-limit headers. The 403s users reported match that limit; the log now tells a limit from other refusals. The app ships no GitHub credentials.
- **Rules:** a release counts only when its version and channel agree and it carries this platform's `latest*.yml`. The feed's download folder must be the repository's GitHub Releases, so the feed can't send the app to files anywhere else; a feed that tries counts as broken. Each channel takes its own highest version, by version order: Stable never sees a nightly, and Nightly never sees a stable release, since each stable release is a nightly that was promoted. Versions 0.0.3 and earlier took the highest of both on Nightly, and still do from the same feed, whose `stable` and `nightly` name each channel's highest release.
- **Schedule** (`services/updates.ts`): a check 20 seconds after starting, then every four hours plus up to a tenth, so installs spread out. An automatic check that fails keeps what the last one found and tries again after 15 minutes, backing off to four hours, and never before GitHub allows it. Checks that overlap share one request. A check never runs while a download is in progress or ready, and one that answers after a download started leaves it alone, so a check can't drop a staged update.
- **The service** holds the channel (set from the build on first launch, then only by the user), the offered release with its notes and page, when it last checked and checks next, the version whose notice was closed, and the download and restart steps. Switching channels drops a downloaded or downloading update the new channel doesn't receive, then checks. Only the latest check counts: one that answers after a newer check or a channel change changes nothing, and download and restart refuse a version the chosen channel doesn't receive. Nightly offers only a nightly newer than the installed build, so a stable build on Nightly waits for the next nightly. On Stable, a nightly build is offered the newest stable release even when it is older; it installs over the nightly and keeps the data. A check that fails keeps the update an earlier one found on offer, the user's own included. `updates.json` is written one change at a time, so the last choice wins, and keeps keys it doesn't know for the newer release that wrote them.
- **The UI:** the top bar's notice (`features/updates/UpdateNotice.tsx`) and the Updates rows in Settings > General read the same status and call the same actions.
- **Store copies:** Electron sets `process.windowsStore` in a process with package identity, which every installed MSIX has, from the Store or sideloaded. `index.ts` then gives the service a way to open the app's Store page (`ms-windows-store://pdp/?ProductId=9N45GG76ZP4T`) instead of discovery and an installer, so electron-updater's updater is never created. The service checks, downloads and installs nothing, writes no `updates.json`, and reports `distribution: "store"`; Settings shows one row with **Open Store**, which calls `updates.openStore`. Only stable releases go to the Store ([releasing](../maintainers/releasing.md#microsoft-store-package)).
- **The installer** (`platform/installer.ts`) wraps electron-updater: generic provider pointed at the chosen release, no automatic download, no install on quit, a check that the metadata names the chosen version, and one download at a time, so a new one waits for a cancelled one to stop. electron-updater keeps a random id in `.updaterId` in the data folder and sends it with each request for update metadata, for staged rollouts, which releases don't use; the installer sends that header empty, so the id stays on the device. On macOS, Squirrel checks the update's signature only when installing, so a refused update surfaces as a failed install, not a failed download.

## Licences

`scripts/licences.ts` writes `out/licences/third-party.json` during the build from the packages the bundles actually contain, plus Electron, Chromium and its FFmpeg, Node.js, Microsoft's Direct3D files, FFmpeg, x264, the MinGW-w64 runtime in the Windows ffmpeg, NSIS and its plug-ins in the Windows setup program, and the app's own GPL-3.0 text; [development](development.md#third-party-notices) describes it. `services/licences.ts` reads it for Settings > About, and turns Chromium's credits page into text on request. About's Source row links to the commit the build comes from, `__BUILD_COMMIT__` from `electron.vite.config.ts`.
